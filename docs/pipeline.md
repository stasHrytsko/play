# Конвейер: архитектура

Как идея превращается в результат. Один артефакт на этап, один источник
правды на сущность, стадия выводится из файлов, а не проставляется руками.

Это целевая архитектура. Что из неё уже есть и в каком порядке двигаться —
в разделе «Миграция» в конце.

---

## Принципы

**Один артефакт на этап.** У каждого этапа ровно один выходной файл. Нет
файла — этап не пройден. Это и есть трекер: не нужна отдельная таблица со
статусами, потому что статус — это наличие файла.

**Стадия выводится, а не хранится.** Никто не пишет `status: built` руками.
Стадия вычисляется из того, какие артефакты существуют. Руками хранится
только то, что нельзя вывести: расписание (какая игра в какой день) и
вердикт (решение человека).

**Шапка для конвейера, проза для человека.** Каждый markdown-документ
начинается с YAML-шапки. Шапку читают скрипты, прозу — человек и AI.
Никакое поле не живёт в двух местах.

**Один слаг на игру, решается один раз.** Слаг придумывается на этапе IDEA
и дальше не меняется нигде: имя файла идеи, имя файла спеки, папка игры,
имя файла данных, имя файла результата, URL на хабе.

---

## Дерево

```
ideas/NN-slug.md          идея — шапка + 8 ответов          ← пишет человек
docs/templates/idea.md    шаблон идеи
specs/NN-slug.md          спека — шапка + 12 разделов      ← пишет AI по идее
app/games/<slug>/         код игры                          ← пишет AI по спеке
data/<slug>.json          воронка, выгруженная из PostHog   ← пишет скрипт
results/NN-slug.md        карточка результата + вердикт     ← пишет AI, утверждает человек

g/<slug>/                 опубликованная играбельная сборка ← кладёт release.mjs
g/assets/                 общие хешированные бандлы всех игр

games.json                реестр: день → слаг, статус, ссылки, даты
specs/front-matter.mjs    чтение YAML-шапок — общее для хаба и дистрибуции
distribution/             тексты постов и генератор расписания
docs/                     решения, архитектура, шаблоны

.claude/skills/           восемь команд конвейера
.github/workflows/ci.yml  CI — переехал в корень, работает
release.mjs               публикация одной игры на хаб
pipeline.mjs              статус конвейера одной командой
```

`NN` — номер концепта, а не день. Концепт 23 может выйти в день 5. Связь
«день → слаг» живёт только в `games.json`.

## Источники правды

Каждая строчка — ровно одно место. Если значение нужно где-то ещё, его
читают, а не копируют.

| Сущность | Источник правды | Кто читает |
|---|---|---|
| Замысел, что проверяем | `ideas/NN-slug.md` | автор спеки |

## Этапы

### 1. IDEA

**Вход:** голова. **Выход:** `ideas/NN-slug.md`. **Делает:** человек, 15 минут.

Единственный этап, где пишется текст руками. Шапка плюс восемь коротких
ответов. Шаблон — `docs/templates/idea.md`.

```yaml
---
slug: overload           # решается здесь и больше не меняется
number: 23
title_ru: Перегруз
title_en: Overload
verb: погрузка
pressure: скрытая прочность троса
twist: ставка            # или null
emotion: азарт на грани провала
family: push-your-luck
levels: generated        # generated | authored
solver: required         # required | none
---
```

Восемь разделов прозой: что делает игрок, что создаёт давление, в чём
необычность, ради какого момента в это играют, победа, поражение, что
проверяет эта игра, kill-критерий. Шапка — ярлыки, проза — картинка; ни одно
значение не пишется дважды.

**Почему kill-критерий пишется здесь, а не в конце:** критерий,
сформулированный после того, как увидел цифры, всегда подгоняется под них.
Записанный до первого захода — работает.

**Ворота:** `node ideas/validate.mjs` — шапка валидна, слаг совпадает с именем
файла, все восемь разделов непусты. Пустая папка ошибкой не считается.

### 2. SPEC

**Вход:** `ideas/NN-slug.md`. **Выход:** `specs/NN-slug.md`. **Делает:** AI.

Шапка идеи копируется в шапку спеки без изменений и дополняется полями,
которые появляются только здесь:

```yaml
score: 27                # оценка по шести критериям
pitch_ru: Вешай ящики на крюк и поднимай партиями — трос выдерживает
          неизвестный вес, а поездок мало.
pitch_en: Load boxes onto the hook and lift them in batches. Nobody says
          what the cable holds, and trips are scarce.
```

`pitch_*` — это то самое «правило одной фразой». Отсюда его берут и карточка
на хабе, и тексты постов. Сегодня оно продублировано в трёх местах.

Проза — двенадцать разделов по `specs/_TEMPLATE.md`: 1–11 описывают игру,
12 — профиль нашей фабрики. Главный критерий не меняется: если из предложения
нельзя написать тест, предложение недописано.

**Ворота:** все двенадцать разделов на месте — неприменимые помечены явно, а
не пропущены; §10 перечисляет только те события, которые шелл реально шлёт.

### 3. BUILD

**Вход:** `specs/NN-slug.md`. **Выход:** `app/games/<slug>/`. **Делает:** AI.

Здесь ничего менять не надо — фабрика уже правильная. Общими остаются
`shell`, `ui-kit`, `render-kit`, аналитика, прогресс, тесты. Уникальны
`mechanic/engine`, `mechanic/levels`, `mechanic/render` и `game.config.ts`.

Границы держит линтер, а не дисциплина: движок физически не может
импортировать Phaser, DOM, шелл или сеть. Vite сам находит новую игру,
Vitest сам подхватывает её тесты, Playwright сам находит e2e —
регистрировать нигде не нужно.

**Ворота:** этап VERIFY.

### 4. VERIFY

**Вход:** `app/games/<slug>/`. **Выход:** зелёный прогон. **Делает:** CI.

Существующие пять ворот (`npm run check`): typecheck, линтер с проверкой
границ, юнит-тесты движка, продакшен-сборка, e2e.

Плюс три, которых нет:

- **Проходимость.** Если в шапке `solver: required` — бот играет на реальном
  `levels.json`. Сравнение с kill-критерием из шапки идеи.
- **Контракт событий.** Механика шлёт ровно тот набор событий, который
  объявлен в `SignalSink`. Ни больше, ни меньше.
- **Кривая сложности.** Уровень 5 не проще уровня 4.

**Ворота:** красный прогон — игра не едет дальше. Работает с 19 сентября:
до этого workflow лежал в `app/.github/`, который GitHub не читает, поэтому
ни один прогон не запускался. Переезд вскрыл три сломанных теста, они
починены.

### 5. RELEASE

**Вход:** зелёная сборка. **Выход:** игра открывается по ссылке. **Делает:**
`release.mjs`.

```sh
node release.mjs <slug>          # опубликовать
node release.mjs <slug> --dry    # показать, что произойдёт, ничего не записав
```

Что делает команда:

1. `npm run typecheck && npm run build` в `app/`.
2. `app/dist/games/<slug>/index.html` → `<корень>/g/<slug>/index.html`, пути к
   ассетам переписываются: в сборке игра лежит на два уровня ниже них, на
   хабе — на один.
3. `app/dist/assets/*` → `<корень>/g/assets/` **дополнительно**. Файлы никогда
   не удаляются: имена хешированные, и у уже опубликованной игры HTML
   ссылается на свой хеш — он обязан остаться рабочим. Sourcemaps не
   копируются, это 12 из 13 мегабайт сборки.
4. В `games.json` проставляются `links.play`, `status: published` и дата.
5. `node build-games.mjs` перерисовывает сетку карточек и страницу игры.

`/g/<slug>/` — играбельная сборка, `/<slug>/` — страница-описание. Два
разных URL для двух разных вещей, без коллизии.

Два предохранителя, оба падают громко:

- нет `app/games/<slug>/game.config.ts` — печатается список собранных игр;
- в `games.json` нет записи с таким слагом — печатается список занятых дней.

Второй существует потому, что слаг спеки и слаг хаба однажды уже разошлись
(`box-arrives` против `incoming-box`). Расхождение снято — слаг теперь один, —
но предохранитель остался: публиковать под другим именем молча значит развести
их снова.

Полные ворота качества — это CI, а не этот скрипт: здесь только быстрая
проверка, что код вообще собирается.

### 6. DISTRIBUTION

**Вход:** `games.json` + `distribution/posts.json`. **Выход:** CSV. **Делает:** скрипт.

Работает. Обе запланированные правки сделаны: расписание берётся из
`games.json` (`schedule.json` удалён), названия и правило одной фразой — из
шапки спеки. В `posts.json` остались только интриги «завтра» и десять постов
прогрева — то, что действительно пишется отдельно, потому что это другое
ремесло.

Проверено тем, что после переключения CSV сошёлся байт в байт, кроме одной
ссылки: день 1 перестал уезжать на `incoming-box` и поехал на `box-arrives`.

### 7. DATA

**Вход:** опубликованная игра. **Выход:** `data/<slug>.json`. **Делает:** скрипт.

Сегодня поток строго односторонний: шелл шлёт в PostHog, обратно не читает
никто, метрики в `games.json` заполняются руками.

Один скрипт, один HogQL-запрос через Query API, одна выгрузка на игру:

```json
{
  "slug": "overload",
  "pulledAt": "2026-10-08T20:00:00Z",
  "windowDays": 7,
  "opened": 412,
  "started": 268,
  "byLevel": { "1": 268, "2": 201, "3": 144, "4": 96, "5": 61 },
  "failed": 173,
  "retried": 118,
  "completed": 61,
  "ratings": { "1": 2, "2": 5, "3": 14, "4": 21, "5": 9 },
  "comments": 7,
  "returnedD1": 44,
  "bySource": { "telegram": 120, "tiktok": 88, "x": 61 }
}
```

Важно: для чтения нужен персональный API-ключ PostHog, а не публичный
проектный токен из `analytics-config.js`. Он не должен попасть в
репозиторий — только переменная окружения.

### 8. RESULT

**Вход:** `data/<slug>.json` + kill-критерий. **Выход:** `results/NN-slug.md`.
**Делает:** AI, утверждает человек.

```yaml
---
slug: overload
verdict: KILL            # KILL | PROMOTE | INCONCLUSIVE
decidedAt: 2026-10-08
players: 412
reachedL5: 23%
returnD1: 11%
rating: 3.4
killCriterionMet: true
---
```

Проза — стандартная карточка: что произошло, сколько игроков, как проходили,
где отваливались, какая оценка, что писали, сработала ли основная идея, что
было интересным, что не сработало.

Вердикт — решение человека, но AI обязан предложить его и обосновать
цифрами. `INCONCLUSIVE` — честный исход при малой выборке, а не способ
отложить решение.

Результаты лежат рядом с историей и читаются при написании следующих идей:
«какое семейство побеждает» становится запросом к папке `results/`, а не
воспоминанием.

## Стадия выводится

Никакого поля `status`, которое надо не забыть поменять. Стадия — это
функция от файлов:

| Стадия | Признак |
|---|---|
| `idea` | есть `ideas/NN-slug.md` |
| `spec` | есть `specs/NN-slug.md` |
| `built` | есть `app/games/<slug>/game.config.ts` |
| `published` | в `games.json` заполнен `links.play` |
| `measured` | есть `data/<slug>.json` |
| `judged` | есть `results/NN-slug.md` с непустым `verdict` |

`node pipeline.mjs status` печатает доску:

```
день  слаг            стадия      вердикт
  1   box-arrives     judged      PROMOTE
  2   two-moves-later published   —
  3   basement        built       —
  4   triple          spec        —
  5   only-green      idea        —
```

Это заменяет гугл-трекер: колонки «собрана / протестирована / опубликована»
перестают быть чек-боксами, которые надо ставить руками.

## Восемь команд

Каждая — один переход, файл на входе, файл на выходе.

| Команда | Вход | Выход | Кто |
|---|---|---|---|
| `/idea` | разговор | `ideas/NN-slug.md` | человек + AI |
| `/spec` | идея | `specs/NN-slug.md` | AI |
| `/build` | спека | `app/games/<slug>/` | AI |
| `/verify` | код | зелёный прогон | CI |
| `/release` | зелёная сборка | сайт + `games.json` | скрипт |
| `/distribute` | реестр + тексты | CSV | скрипт |
| `/pull-data` | опубликованная игра | `data/<slug>.json` | скрипт |
| `/result` | данные + критерий | `results/NN-slug.md` | AI + человек |

Четыре средних — `build`, `verify`, `release`, `distribute` — должны быть
полностью автоматическими. `idea` требует человека по существу. `result`
требует его согласия с вердиктом.
