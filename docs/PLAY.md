# PLAY — конвейер игровых прототипов

## Что такое PLAY

**PLAY — это стандартизированный конвейер производства небольших игровых прототипов.**

Его задача — не автоматизировать всё подряд и не превращать разработку идеи в
сложный экспериментальный процесс.

Главная цель PLAY:

> взять новую игровую идею и каждый раз провести её через один и тот же понятный
> путь до работающего, проверенного и опубликованного прототипа.

Идеи могут быть совершенно разными. Стандарт производства остаётся одинаковым.

Высокоуровнево:

```text
IDEA → SPEC → GAME → CHECK → REVIEW → RELEASE → DISTRIBUTION → FEEDBACK
```

PLAY нужен для трёх вещей:

1. **Единый стандарт.** Каждая игра описывается, собирается и проверяется по
   одинаковым правилам.
2. **Скорость.** Общие части игры не создаются заново для каждого прототипа.
3. **Повторяемость.** Следующую игру можно запустить по тому же процессу без
   изобретения нового workflow.

PLAY — это не научная лаборатория, не A/B-платформа и не полноценный production
pipeline большой студии. Это лёгкая фабрика прототипов для одного автора + AI.

---

## Из чего состоит PLAY

PLAY состоит из двух частей: **framework** и **production flow**.

### 1. Framework — то, что уже готово и переиспользуется

Framework отвечает на вопрос:

> Что не нужно создавать заново для каждой следующей игры?

Общая база находится в `app/`.

В неё входят:

- **Shell** — меню, onboarding, выбор уровней, навигация, win/fail flow, rating.
- **UI Kit** — общие интерфейсные элементы.
- **Render Kit** — общие визуальные эффекты для игровых сцен.
- **Progress** — сохранение прогресса.
- **Analytics** — единые события поведения игрока.
- **Feedback** — рейтинг и комментарий после прохождения.
- **Tests / build rules** — единый стандарт технической проверки.
- **Release tooling** — единый способ собрать и опубликовать игру.

У конкретной игры меняется в основном:

```text
rules
engine
levels
render / input
game config
```

То есть новая игра не строится с нуля. Она подключает новую механику к общей
платформе PLAY.

## 2. Production flow — как производится одна игра

### Шаг 1 — IDEA

**Ответственный: человек.**

Автор придумывает игровую идею и объясняет её AI обычным человеческим языком.

Идея может прийти сообщением, голосом, заметкой или коротким наброском.
Заполнять большой GDD не нужно.

Минимально из идеи должны быть понятны:

- что делает игрок;
- в чём основной игровой глагол;
- что создаёт давление / ограничение;
- в чём интерес или необычность механики;
- что считается победой;
- что считается поражением, если оно есть;
- какое ощущение должна дать игра.

Если чего-то не хватает, AI сначала нормализует идею до понятного brief.

**Обязательного файла на этом шаге нет.** PLAY не должен создавать бюрократию
ради самой бюрократии.

Выход этапа: достаточно ясная идея, из которой можно написать спецификацию.

```text
human idea
    ↓
AI normalization
    ↓
ready for spec
```

---

### Шаг 2 — SPEC

**Ответственный: AI.**

AI превращает идею в строгую спецификацию по единому шаблону
`specs/_TEMPLATE.md`.

Спецификация должна быть настолько однозначной, чтобы следующий исполнитель
мог собрать игру без самостоятельного изобретения правил.

Канонический результат этапа:

```text
specs/<NN>-<slug>.md
```

Spec — источник правды для конкретной игры до начала реализации.

Дополнительные рекомендации по написанию спеки находятся в
`specs/HOWTO.md`.

---

### Шаг 3 — BUILD

**Ответственный: AI + PLAY framework.**

По готовой spec AI создаёт игру внутри:

```text
app/games/<slug>/
```

AI не создаёт новый shell, систему аналитики, меню, рейтинг или общий UI для
каждой игры.

Он реализует только уникальную часть игры и подключает её к существующему
framework.

Типовая структура:

```text
game.config.ts
mechanic/
  engine/
  levels/
  render/
tests/
rules.md
```

Главный принцип:

> Spec описывает правила. Framework даёт стандарт. Mechanic делает конкретную
> игру.

---

### Шаг 4 — CHECK

**Ответственный: автоматика + AI.**

Игра проходит общий технический контроль.

Базовая точка входа:

```sh
npm run check
```

Проверяются типы, lint, unit tests, build и E2E в соответствии с текущей
конфигурацией `app/`.

Если проверка не проходит, AI исправляет реализацию. Сломанная игра не должна
переходить к публикации.

Выход этапа:

```text
green build
```

---

### Шаг 5 — HUMAN REVIEW

**Ответственный: человек.**

Это намеренно ручной этап.

Автор сам открывает прототип и проверяет не только техническую корректность,
но и ощущение от игры:

- понятна ли механика;
- приятно ли играть;
- соответствует ли прототип исходной идее;
- нет ли очевидных визуальных или UX-проблем;
- готов ли этот вариант показываться другим людям.

AI может исправлять найденные проблемы, но финальное решение
**«публикуем»** остаётся за человеком.

---

### Шаг 6 — RELEASE

**Ответственный: человек запускает, автоматика выполняет.**

После одобрения игра публикуется единым release-процессом:

```sh
node release.mjs <slug>
```

Release tooling:

- проверяет игру;
- собирает `app/`;
- публикует playable build;
- обновляет данные релиза;
- пересобирает PLAY Hub.

Публичная playable-версия получает адрес:

```text
/g/<slug>/
```

Страница игры на PLAY Hub:

```text
/<slug>/
```

---

### Шаг 7 — DISTRIBUTION

**Ответственный: AI + человек.**

После готовности игры AI подготавливает контент для публикации:

- короткое описание игры;
- текст поста;
- hook / teaser;
- описание механики простыми словами;
- CTA / ссылку на игру;
- при необходимости варианты для разных каналов.

Материалы распределения живут в `distribution/`.

AI готовит материалы, человек контролирует финальную подачу и публикацию там,
где автоматическая публикация не настроена.

Это часть производственного процесса: прототип считается реально выпущенным,
когда до него могут дойти игроки, а не когда существует только build.

---

### Шаг 8 — FEEDBACK

**Ответственные: PLAY framework + игроки + человек.**

После релиза общая система собирает стандартные сигналы:

- открытие игры;
- старт уровня;
- первое реальное действие;
- победы и поражения;
- повторные попытки;
- прохождение всех уровней;
- рейтинг 1–5;
- комментарий игрока.

Эти данные не меняют процесс производства самой игры. Они нужны автору, чтобы
после публикации понять реакцию людей и решить, что делать с идеей дальше.

PLAY не обязан автоматически принимать продуктовые решения за автора.

---

## Кто что делает

| Участник | Ответственность |
| --- | --- |
| **Человек** | Придумывает идею, оценивает прототип, принимает решение о публикации и дальнейшем развитии |
| **AI** | Структурирует идею, пишет spec, реализует механику, исправляет ошибки, готовит тексты и материалы для дистрибуции |
| **PLAY framework** | Даёт общий shell, UI, render helpers, progress, analytics, feedback и технические контракты |
| **Автоматика** | Проверяет, собирает и публикует игру |
| **Игроки** | Играют и дают реальные поведенческие сигналы, оценки и комментарии |

---

## Что является стандартом

Для каждой следующей игры мы **не придумываем заново**:

- формат спецификации;
- количество уровней и shell-flow;
- базовую архитектуру игры;
- UI primitives;
- визуальные helpers;
- систему прогресса;
- аналитику;
- feedback;
- способ тестирования;
- способ сборки;
- способ публикации;
- базовый формат материалов для дистрибуции.

Мы придумываем заново только то, ради чего вообще существует новый прототип:

> **саму игровую механику и игровой опыт.**

## Короткое определение конвейера PLAY

> **Конвейер PLAY — это повторяемый процесс, в котором человек приносит новую
> игровую идею, AI превращает её в стандартную спецификацию и собирает игру на
> общей технической базе, автоматика проверяет сборку, человек принимает
> финальное решение о публикации, а после релиза PLAY приводит игроков и
> собирает их реакцию.**
