# PLAY — конвейер игровых прототипов

## Что такое PLAY

**PLAY — это стандартизированный конвейер производства небольших игровых прототипов.**

Его задача — не автоматизировать всё подряд и не превращать разработку идеи в
сложный экспериментальный процесс.

Главная цель PLAY:

> взять новую игровую идею и каждый раз провести её через один и тот же понятный
> путь до работающего, проверенного и опубликованного прототипа.

Идеи могут быть совершенно разными. Стандарт производства остаётся одинаковым.

Высокоуровнево:

```text
TRENDS → IDEA → [gate 1] → SPEC → [gate 2] → BUILD → [gate 3: CI]
       → [gate 4: человек играет] → MEDIA → RELEASE → DISTRIBUTION → VERDICT
```

Четверо ворот, и трое из них — решение человека. Автоматика проверяет, что
игра не падает и что цифры не подделаны; что стоит делать, решает автор.

PLAY нужен для трёх вещей:

1. **Единый стандарт.** Каждая игра описывается, собирается и проверяется по
   одинаковым правилам.
2. **Скорость.** Общие части игры не создаются заново для каждого прототипа.
3. **Повторяемость.** Следующую игру можно запустить по тому же процессу без
   изобретения нового workflow.

PLAY — это не научная лаборатория, не A/B-платформа и не полноценный production
pipeline большой студии. Это лёгкая фабрика прототипов для одного автора + AI.

---

## Из чего состоит PLAY

PLAY состоит из двух частей: **framework** и **production flow**.

### 1. Framework — то, что уже готово и переиспользуется

Framework отвечает на вопрос:

> Что не нужно создавать заново для каждой следующей игры?

Общая база находится в `app/`.

В неё входят:

- **Shell** — меню, onboarding, выбор уровней, навигация, win/fail flow, rating.
- **UI Kit** — общие интерфейсные элементы.
- **Render Kit** — общие визуальные эффекты для игровых сцен.
- **Progress** — сохранение прогресса.
- **Analytics** — единые события поведения игрока.
- **Feedback** — рейтинг и комментарий после прохождения.
- **Tests / build rules** — единый стандарт технической проверки.
- **Release tooling** — единый способ собрать и опубликовать игру.

У конкретной игры меняется в основном:

```text
rules
engine
levels
render / input
game config
```

То есть новая игра не строится с нуля. Она подключает новую механику к общей
платформе PLAY.

## 2. Production flow — как производится одна игра

### Шаг 0 — ТРЕНДЫ

**Ответственный: человек.**

Наблюдения по рынку копятся в `trends/YYYY-MM-DD-тема.md`. Формат свободный,
ворот нет, это сырьё, а не артефакт. Единственное требование — дата в имени
файла: ценность папки в динамике, а не в отдельной записи.

Отсюда берётся рыночный балл на Gate 1. Если балл высокий, а в `trends/` за
последние месяцы об этом ничего — балл выдуман.

---

### Шаг 1 — IDEA

**Ответственный: человек. Оценивает AI, решает человек.**

Автор пишет идею руками, пятнадцать минут, по шаблону
`docs/templates/idea.md`. Восемь коротких разделов: что делает игрок, что
создаёт давление, в чём необычность, ради какого момента играют, победа,
поражение, что проверяем, **kill-критерий**.

Канонический результат этапа:

```text
ideas/active/<NN>-<slug>.md
```

Файл обязателен. Здесь же решается слаг — один раз и навсегда: он станет
именем файла спеки, папкой игры, ключом в дистрибуции и адресом на хабе.

**Kill-критерий пишется здесь, а не в конце.** Условие, при котором концепт
хоронится, а не чинится, работает только если сформулировано до первых цифр.
Записанный после — всегда подогнан под них; это свойство чтения чисел, а не
вопрос дисциплины.

---

### GATE 1 — оценка идеи

**Считает AI, решает человек.**

AI дописывает в файл раздел «Оценка»: шесть критериев по 1–5 со строкой
обоснования на каждый, саммари и итог.

| Критерий | Что оценивается |
|---|---|
| `readability` | Понятно ли правило с первого взгляда |
| `motivation` | Хочется ли сделать следующий ход |
| `pressure` | Есть ли настоящее давление |
| `payoff` | Чувствуется ли награда за хороший ход |
| `producibility` | Собирается ли за один вечер на общей базе |
| `market` | Попадает ли в то, что сейчас работает |

**Порог: сумма ≥ 24 из 30 и `producibility` ≥ 3.** Второе не компенсируется
суммой — игра делается за вечер, и три дня работы отнимают три прототипа.

Дальше решает человек: `gate1: approved` с датой — идея едет в спеку;
`gate1: rejected` — файл переезжает в `ideas/rejected/` с одной строкой
почему. Отказ не удаляется: история отказов не даёт через месяц зайти на тот
же круг.

Проверка: `node ideas/validate.mjs`. Скрипт не решает за человека — он ловит
`approved` вопреки цифрам и не даёт спеке появиться раньше одобрения.

---

### Шаг 2 — SPEC

**Ответственный: AI.**

AI превращает одобренную идею в строгую спецификацию по единому шаблону
`specs/_TEMPLATE.md`. Шапка идеи переезжает **без изменений** и дополняется
только `pitch_ru` и `pitch_en` — формулировка «правило одной фразой»
рождается, когда игра уже описана.

Спецификация должна быть настолько однозначной, чтобы следующий исполнитель
собрал игру без изобретения правил. Главный критерий: если из предложения
нельзя написать тест — предложение недописано.

Канонический результат этапа:

```text
specs/<NN>-<slug>.md
```

Дополнительные рекомендации — `specs/HOWTO.md`.

---

### GATE 2 — спека принята

**Проверяет скрипт, решает человек.**

`node specs/validate.mjs`: шапка на месте, слаг совпадает с именем файла,
шапка не разошлась с идеей, §10 требует только тех событий, которые шелл
реально шлёт, разделы не пропущены.

Дальше спеку читает человек и ставит в шапку `review: approved` с датой —
или `review: rework` и раздел «Замечания» списком внизу файла. При `rework`
спека возвращается на доработку; в сборку идёт только `approved`.

---

### Шаг 3 — BUILD

**Ответственный: AI + PLAY framework.**

По готовой spec AI создаёт игру внутри:

```text
app/games/<slug>/
```

AI не создаёт новый shell, систему аналитики, меню, рейтинг или общий UI для
каждой игры.

Он реализует только уникальную часть игры и подключает её к существующему
framework.

Типовая структура:

```text
game.config.ts
mechanic/
  engine/
  levels/
  render/
tests/
rules.md
```

Главный принцип:

> Spec описывает правила. Framework даёт стандарт. Mechanic делает конкретную
> игру.

---

### GATE 3 — CI

**Ответственный: автоматика.**

```sh
npm run check
```

Типы, линтер с проверкой архитектурных границ, юнит-тесты движка,
продакшен-сборка, e2e. Границы держит линтер, а не дисциплина: движок
физически не может импортировать Phaser, DOM, шелл или сеть.

Красный прогон — игра не едет дальше, AI чинит и гоняет снова, пока не
зелёный. Плюс отдельно проверяются спеки и идеи:
`node specs/validate.mjs`, `node ideas/validate.mjs`.

Выход этапа:

```text
green build
```

---

### GATE 4 — человек играет

**Ответственный: человек.**

Намеренно ручной этап. Зелёный прогон говорит, что игра не падает. Он не
говорит, понятна ли она, приятно ли в неё играть и не стыдно ли показывать.

Автор открывает прототип и смотрит:

- понятна ли механика без слов, с первого хода;
- случился ли тот момент, ради которого играют, — раздел 4 файла идеи;
- есть ли реакция на каждое действие, включая запрещённый ход и проигрыш;
- не легче ли пятый уровень четвёртого;
- отправил бы он на это ссылку человеку, чьё мнение важно.

Решение записывается файлом:

```text
app/games/<slug>/review.md
```

Шапка `review: approved | rework | pending` с датой, ниже журнал заходов —
новое сверху, старое не стирается. Шаблон: `docs/templates/review.md`.

`rework` возвращает игру на шаг 3. Кругов может быть сколько угодно, но если
их больше трёх — дело обычно не в сборке, а в недописанной спеке, и
возвращаться надо туда.

**`release.mjs` отказывается публиковать игру, у которой `review` не
`approved`.** Так это ворота, а не привычка, которую однажды вечером в спешке
пропустят.

---

### Шаг 5 — МЕДИА

**Ответственный: машина + человек.**

В папке игры появляется `media/`: обложка, баннер, скриншот, ролик и тексты
про эту игру. Скриншот и ролик снимает Playwright — он и так ходит по игре в
e2e. Обложку и баннер делает человек: сгенерированная обложка выдаёт себя
мгновенно и работает против доверия к прототипу.

Ролик не коммитится — тридцать видео превратили бы репозиторий, который
хостится как есть, в сотни мегабайт. Он лежит локально, планировщик берёт его
с диска. Подробности — `docs/templates/media.md`.

---

### Шаг 6 — RELEASE

**Ответственный: человек запускает, автоматика выполняет.**

После одобрения игра публикуется единым release-процессом:

```sh
node release.mjs <slug>
```

Что делает команда:

1. отказывается публиковать, если `review.md` не `approved` — Gate 4;
2. отказывается публиковать слаг, которого нет в `games.json`;
3. `npm run typecheck && npm run build` в `app/`;
4. кладёт сборку в `g/<slug>/`, переписывая пути к ассетам;
5. копирует картинки из `media/` игры (ролик — нет, он не коммитится);
6. проставляет `links.play`, `status: published` и дату в `games.json`;
7. пересобирает хаб.

Ассеты копируются **дополнительно и никогда не удаляются**: имена хешированы,
и HTML уже вышедшей игры ссылается на свой хеш — он обязан остаться рабочим,
иначе игра поменяется задним числом.

Два адреса, намеренно разные:

```text
/g/<slug>/     играбельная сборка
/<slug>/       страница с описанием и цифрами
```

День выхода живёт в `games.json` — расписание день → слаг, и слаг там обязан
совпадать с именем файла спеки.

---

### Шаг 7 — DISTRIBUTION

**Ответственный: AI + человек.**

После готовности игры AI подготавливает контент для публикации:

- короткое описание игры;
- текст поста;
- hook / teaser;
- описание механики простыми словами;
- CTA / ссылку на игру;
- при необходимости варианты для разных каналов.

Материалы распределения живут в `distribution/`.

AI готовит материалы, человек контролирует финальную подачу и публикацию там,
где автоматическая публикация не настроена.

Это часть производственного процесса: прототип считается реально выпущенным,
когда до него могут дойти игроки, а не когда существует только build.

---

### Шаг 8 — ЦИФРЫ И ВЕРДИКТ

**Ответственные: framework + игроки; вердикт предлагает AI, утверждает человек.**

После релиза общая система собирает стандартные сигналы: открытие игры, старт
уровня, первое реальное действие, победы и поражения, повторные попытки,
прохождение всех пяти, рейтинг 1–5, комментарий.

**Окно измерения — месяц с даты релиза.** Скрипт выгружает воронку в
`data/<slug>.json`, AI пишет карточку результата `results/NN-slug.md` со
сверкой с kill-критерием из шапки идеи — дословно, он для того и был
записан заранее.

Правило вердикта решает **долю дошедших до конца**, а не абсолютное число:
игра первого дня выходит на аудиторию в тридцать человек, игра тридцатого —
на выросшую за месяц, и абсолютные числа между ними несравнимы.

| Условие | Вердикт |
|---|---|
| 30+ прохождений и доля от открытий ≥ 25% | **PROMOTE** |
| 30+ прохождений и доля ≤ 10% | **KILL** |
| 30+ прохождений, доля между | решает человек по повторам и возвратам |
| меньше 30 прохождений | **INCONCLUSIVE** |

Тридцать — минимум, при котором доля вообще что-то значит: там доверительный
интервал около ±8 процентных пунктов, и 25% отличимо от 10%. На десяти
прохождениях интервал шире самой разницы.

Рейтинг учитывается последним и только от 30 оценок: оценку ставят дошедшие
до конца, то есть те, кому уже понравилось, а отвалившиеся молча уходят.

Победители собираются в индекс `results/PROMOTED.md`. Код никуда не
копируется — копия разойдётся с оригиналом на первой же правке.

`results/` становится входом для следующих идей: «какое семейство побеждает»
— запрос к папке, а не к памяти.

## Где что стоит

Стадия нигде не хранится — она считается из того, какие файлы существуют.

```sh
node pipeline.mjs            # доска целиком
node pipeline.mjs --waiting  # только то, что ждёт решения человека
node pipeline.mjs --write    # обновить снимок для страницы dashboard/
```

Три из четырёх ворот — решение человека, и ровно они теряются первыми в
вечер, когда некогда. `--waiting` отвечает на единственный вопрос, который
задают утром: за что браться.

### Правило: доска не отстаёт от репозитория

**Доска всегда показывает текущее состояние.** Делать для этого ничего не
нужно, и это сознательно: правило, которое держится на памяти, — не правило.

Стадии нигде не хранятся, они считаются из файлов. Снимок `status.json` не
коммитится — его собирает Vercel на каждом пуше. Всё, что зависит от даты
(обратный отсчёт, «месяц вышел», «снять цифры»), страница пересчитывает в
браузере, поэтому висящая на экране вкладка не устаревает и без деплоя.

Пуш обновляет то, что зависит от файлов; открытая вкладка — то, что зависит
от даты.

Причина: доска, которая показывает вчерашнее состояние и выглядит при этом
свежей, — худший способ сломаться. Ей верят и по ней принимают решения.
**Пустая доска честнее отставшей.** Подробности — `CLAUDE.md`, правило №1.

## Кто что делает

| Участник | Ответственность |
| --- | --- |
| **Человек** | Пишет идею и kill-критерий, проходит четверо ворот: Gate 1 — одобряет идею, Gate 2 — принимает спеку, Gate 4 — играет и решает публиковать, и утверждает финальный вердикт |
| **AI** | Оценивает идею по шести критериям, пишет spec, реализует механику, чинит до зелёного, готовит медиа и тексты, предлагает вердикт с обоснованием |
| **PLAY framework** | Даёт общий shell, UI, render helpers, progress, analytics, feedback и технические контракты |
| **Автоматика** | Проверяет, собирает и публикует игру |
| **Игроки** | Играют и дают реальные поведенческие сигналы, оценки и комментарии |

## Что является стандартом

Для каждой следующей игры мы **не придумываем заново**:

- формат спецификации;
- количество уровней и shell-flow;
- базовую архитектуру игры;
- UI primitives;
- визуальные helpers;
- систему прогресса;
- аналитику;
- feedback;
- способ тестирования;
- способ сборки;
- способ публикации;
- базовый формат материалов для дистрибуции.

Мы придумываем заново только то, ради чего вообще существует новый прототип:

> **саму игровую механику и игровой опыт.**

```text
      пишет идею и       │   IDEA   │  ideas/active/NN-slug.md

                              ↓
                         ┌──────────┐
                         │   SPEC   │  specs/NN-slug.md

                      ◆ GATE 2 ◆   валидатор + человек: approved | rework
                              ↓
                ┌─────────────────────────┐

                │ Progress / Analytics    │

                         │  BUILD   │  app/games/<slug>/

                              ↓

                              ↓
                      ◆ GATE 4 ◆   человек играет сам
                              │      app/games/<slug>/review.md
                              ↓
                         ┌──────────┐
                         │  MEDIA   │  обложка, баннер, скриншот, ролик, тексты
                         └────┬─────┘
                              ↓
                         ┌──────────┐
                         │ RELEASE  │  node release.mjs <slug>
                         └────┬─────┘
                 ┌────────────┴────────────┐
                 ↓                         ↓
          ┌──────────────┐          ┌──────────────┐
          │ DISTRIBUTION │          │   PLAY HUB   │

                              │

```

## Короткое определение конвейера PLAY

> **Конвейер PLAY — это повторяемый процесс, в котором человек приносит новую
