# 1. Паспорт концепта

Поля паспорта — в шапке раздела 0.

**Почему kill-критерий именно такой.** Вся идея в том, что смешивание необратимо: одна неверная пропорция даёт бурый, и его уже не разделить. Значит, игрок обязан отказываться от соблазнительных смешиваний. Если жадная стратегия «смешивай при первой возможности» решает большинство уровней, отказываться не приходится ни разу, preview результата становится украшением, а необратимость — декорацией. Провал по критерию означает, что цена ошибки не создаёт сдержанности: это свойство идеи, потому что при выигрышной жадности объёмы и вместимости ничего не меняют.

# 2. Цель и условия

Правила уровня — текст в кнопке «?»:

Перед тобой сосуды с жидкостями и банка-цель. Перетаскивай один сосуд на другой, чтобы перелить всё его содержимое. Если в сосуде уже есть другой цвет, жидкости смешаются.

Красный + жёлтый = оранжевый.
Жёлтый + синий = зелёный.
Синий + красный = фиолетовый.

Смешивать разные цвета можно только в равных объёмах. Если пропорция не 1:1 или ты смешал цвет с уже полученным вторичным цветом, получится бурый. Бурый больше нельзя разделить или исправить.

Перед отпусканием всегда показывается результат переливания.

Собери в банке-цели указанный объём зелёного.

- Условие ПОБЕДЫ: в банке-цели находится ровно `targetVolume` единиц жидкости, весь этот объём имеет цвет `green`.
- Условие ПОРАЖЕНИЯ: после подтверждённого переливания solver определяет, что из текущего состояния больше не существует последовательности легальных действий, способной выполнить условие победы.
- Runtime RNG нет. Начальные цвета, объёмы, вместимость сосудов и целевой объём заранее зафиксированы уровнем.

# 3. Правила

1. На старте уровня движок загружает рабочие сосуды, их содержимое, банку-цель и требуемый объём зелёного.
2. Каждый рабочий сосуд содержит либо одну однородную жидкость, либо пуст.
3. У каждой жидкости есть `color` и целочисленный `volume`.
4. Игрок перетаскивает один рабочий сосуд на другой рабочий сосуд или на банку-цель.
5. Во время drag над сосудом назначения показывается предварительный результат действия: итоговый цвет и объём либо запрет действия.
6. Если игрок отпускает сосуд вне допустимой цели, состояние не меняется и ход не считается.
7. Если сосуд назначения пуст, всё содержимое источника переливается в него без смешивания.
8. После полного переливания источник становится пустым.
9. Если в источнике и назначении один цвет, жидкости объединяются, если суммарный объём не превышает вместимость назначения.
10. Объединение одинакового цвета не считается смешиванием разных цветов и не требует равенства объёмов.
11. Если цвета разные и оба относятся к первичным цветам `red`, `yellow`, `blue`, движок сравнивает их объёмы.
12. Если объёмы разных первичных цветов равны, всё содержимое источника и назначения объединяется в один новый цвет по фиксированной таблице рецептов.
13. `red + yellow` даёт `orange`.
14. `yellow + blue` даёт `green`.
15. `blue + red` даёт `purple`.
16. Порядок источника и назначения в рецепте значения не имеет.
17. Объём результата равен сумме двух исходных объёмов.
18. Если разные первичные цвета имеют разные объёмы, результат всего содержимого назначения становится `brown`.
19. Если хотя бы один из двух разных цветов уже является `green`, `orange`, `purple` или `brown`, результат всего содержимого назначения становится `brown`.
20. `brown` нельзя разделить, восстановить в исходные цвета или преобразовать в другой цвет.
21. Переливание запрещено, если итоговый объём превысит вместимость сосуда назначения.
22. Запрещённое переливание не меняет состояние и не считается ходом.
23. Банка-цель принимает только жидкость цвета `green`.
24. Попытка перелить в банку-цель любой другой цвет запрещена и не считается ходом.
25. Зелёная жидкость переливается в банку-цель целиком; частичные переливания отсутствуют.
26. Если зелёной жидкости больше, чем свободного места в банке-цели, переливание запрещено.
27. После каждого подтверждённого переливания увеличивается `moves` на 1.
28. После каждого подтверждённого переливания сначала проверяется условие победы из п.2.
29. Если победы нет, solver проверяет, существует ли хотя бы один путь к точному `targetVolume` зелёного из текущего состояния.
30. Если такого пути нет, фиксируется поражение по условию из п.2.

# 4. Состояние уровня

```ts
type ColorId =
  | 'red'
  | 'yellow'
  | 'blue'
  | 'green'
  | 'orange'
  | 'purple'
  | 'brown';

type Liquid = {
  color: ColorId;
  volume: number;
};

type VesselState = {
  id: string;
  capacity: number;
  liquid: Liquid | null;
};

type GameState = {
  vessels: VesselState[];
  target: {
    capacity: number;
    greenVolume: number;
    targetVolume: number;
  };
  moves: number;
  status: 'playing' | 'won' | 'failed';
};
```

# 5. Ввод

```ts
{
  type: 'drag';
  sourceId: string;
  targetId: string;
}
```

Один игровой жест — drag одного сосуда на другой сосуд или на банку-цель.

Renderer может локально показывать preview во время drag, но движок получает действие только после отпускания на конкретную цель.

# 6. Контент уровня

Пример `levels.json`:

```json
{
  "id": 1,
  "targetVolume": 6,
  "targetCapacity": 6,
  "vessels": [
    { "id": "v1", "capacity": 4, "color": "green", "volume": 2 },
    { "id": "v2", "capacity": 4, "color": "yellow", "volume": 2 },
    { "id": "v3", "capacity": 4, "color": "blue", "volume": 2 },
    { "id": "v4", "capacity": 4, "color": null, "volume": 0 }
  ]
}
```

Все объёмы целочисленные. Частичных переливаний нет.

Генератор:

1. Создаёт фиксированный набор сосудов, цветов и объёмов.
2. Гарантирует, что стартового зелёного недостаточно для победы.
3. Гарантирует, что хотя бы одно смешивание `yellow + blue` обязательно.
4. Добавляет альтернативные допустимые смешивания, которые могут создать `orange`, `purple` или `brown` и изменить доступные ресурсы.
5. Solver подтверждает наличие хотя бы одного решения.
6. Solver вычисляет долю состояний, где жадное правило «смешай любую доступную правильную пару сразу» совпадает с решением.
7. Невалидные по kill-критерию уровни отбрасываются до публикации.
8. Runtime RNG отсутствует.

Кривая по пяти уровням:

1. 4 сосуда. Уже есть немного зелёного и ровно одна очевидная пара `yellow + blue`. Игрок учится смешивать 1:1 и переливать зелёный в цель.
2. 5 сосудов. Появляется пара первичных цветов с неравными объёмами; preview впервые показывает будущий `brown`. Ошибку можно избежать без сложного планирования.
3. 6 сосудов. Первый настоящий выбор: доступны две корректные пары первичных цветов, но раннее создание ненужного вторичного цвета расходует компонент, необходимый для зелёного.
4. 7 сосудов. Есть несколько одинаковых цветов разного объёма. Сначала нужно объединить одинаковые жидкости, чтобы получить правильную пропорцию для будущего `yellow + blue`.
5. 8 сосудов. Минимум три точки выбора, где смешивание «при первой возможности» ведёт в тупик, а правильное решение требует заранее сохранить конкретный объём синего или жёлтого.

# 7. Визуал

- Рабочие сосуды: простые прозрачные колбы одинаковой формы, отличающиеся содержимым через token-цвета.
- Объём жидкости читается высотой заполнения и маленьким числом внутри сосуда.
- Банка-цель визуально крупнее и отделена от рабочих сосудов; на ней показано `зелёный: N / targetVolume`.
- Выбрано: источник слегка приподнимается при drag.
- Preview: над сосудом назначения появляется маленькая карточка `результат → зелёный 4`, `→ оранжевый 4` или `→ бурый 5` до отпускания.
- Валидный transfer: жидкость одним коротким потоком переливается в назначение.
- Смешивание: две жидкости на долю секунды закручиваются и становятся итоговым цветом.
- Payoff: получение зелёного сопровождается коротким чистым смешиванием без дополнительных эффектов; сразу видно, сколько зелёного стало доступно.
- Ошибка: при получении `brown` жидкость мутнеет за один быстрый переход; если после этого решения больше нет, сразу показывается fail.
- Невалидный target: сосуд мягко возвращается на место, состояние не меняется.
- HUD: `Цель: зелёный N / targetVolume`, `Ходы: N`.

# 8. Онбординг

1. Тебе нужен зелёный — стартового объёма не хватит.
2. Перетащи один сосуд на другой, чтобы перелить жидкость.
3. Жёлтый + синий в равных объёмах дают зелёный.
4. Перед отпусканием ты всегда видишь результат смешивания.
5. Неверная пропорция или лишнее смешивание дают бурый — его уже не исправить.
6. Собери точный объём зелёного в банке-цели.

Кнопка `?` показывает только правило из п.2 и таблицу трёх рецептов; она не повторяет пошаговое обучение.

# 10. Метрики и события

Аналитикой владеет общий shell. Механика **не вызывает PostHog напрямую** —
она сообщает о происходящем через контракт `MechanicHost`.

- Shell сам логирует `game_open`, `help_open`, `level_start`, `level_win`,
  `level_5_complete`, `rating_submit`, `comment_submit`.
- Hub отдельно логирует `hub_impression`, `hub_click`, `teaser_click`.
- D1/D7 и повторные сессии PostHog считает сам по persisted distinct_id и
  `game_open` — отдельные события для них не нужны.
- `retry` шлёт shell после fail-попапа; `level_5_complete` отдельно не
  эмитится, он выводится из `level_win` пятого уровня.

Ниже описано, **когда** наступает каждое событие. Механика при этом вызывает
только `onFirstAction()`, `onFail('<код>')` и `onComplete()` — остальное
отправляет shell.

- `first_action` — первый подтверждённый drag, который реально перелил жидкость из одного сосуда в другой или в банку-цель.
- `level_start` — при входе на каждый уровень с номером уровня.
- `level_win` — когда банка-цель содержит ровно `targetVolume` зелёного.
- `level_fail` — когда после подтверждённого действия solver возвращает `solvable === false`; `reason: 'no_solution'`.
- `retry` — повтор того же уровня после `level_fail`.
- `level_5_complete` отдельно не эмитится.

Kill-критерий концепта: если жадная стратегия «смешивай подходящие цвета при первой возможности» решает более 80% сгенерированных уровней, концепт хоронится.

Онлайн-резерв: читаемость, доходимость до 5 уровня, возврат D1. Если критерий не сработал — концепт хоронится, а не чинится.

# 11. Крайние случаи

- **Повторное то же действие** — после переливания источник пуст (п.8), повторять нечего. Запрещённое действие состояние не меняет (п.22), поэтому повтор даёт ровно тот же отказ.
- **Drop мимо всего** — отпускание вне допустимой цели не меняет состояние и ходом не считается (п.6).
- **Действие невозможно** — запрещённые переливания — превышение вместимости, незелёный цвет в банку, нехватка места под зелёное — не меняют состояние и не тратят ход (п.22, 24, 26). Состояние, где легальных действий нет вовсе, солвер объявляет поражением по п.2 — оно проверяется после каждого подтверждённого переливания (п.29).
- **Ходов не осталось, победа не выполнена** — неприменимо: лимита ходов нет, конец уровня определяет солвер, а не счётчик.
- **Два объекта в одной позиции** — неприменимо: сосуд всегда содержит либо одну однородную жидкость, либо пуст (п.2).

# 12. Профиль реализации

Относится к фабрике, а не к игровой идее: сменится фабрика — перепишется
только этот раздел.

**Контракт.** Механика реализует `MechanicHost` из `src/shell-contract.ts` и
вызывает `onFirstAction()`, `onComplete()`, `onFail(reason)`, `onExit()`.
PostHog напрямую не трогает — см. раздел 10.

**`game.config.ts`.** `id` совпадает со `slug` из шапки, `title` — с
`title_ru`, `tagline` — короткая строка под названием, `levelCount: 5`,
`version` и `onboarding.version` поднимаются при изменении контента и правил
соответственно. Токены аналитики и ключ обратной связи копируются из
`games/tap-targets/game.config.ts`.

**`data-testid`.** Обязателен на каждом интерактивном элементе — e2e ищет
строго по ним. Существующая конвенция: `game-surface` — контейнер механики,
`mechanic-hud` — HUD с атрибутом `data-remaining`.

**Анимация.** Payoff строится из эффектов `render-kit`: `punch`,
`invalidShake`, `successFlash`, `fadeCollapse`, `cameraShake`, `moveTo`.
Если нужного нет — сказать здесь, а не изобретать свой во время сборки.
_Какие именно эффекты нужны этой игре — не записано._
