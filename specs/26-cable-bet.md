# 1. Паспорт концепта

Поля паспорта — в шапке раздела 0.

**Почему kill-критерий именно такой.** Идея в том, что запас кабеля общий на весь уровень, а пары внутри цвета заранее не назначены: дешёвое соединение сейчас может сделать следующее невозможным — и потраченным метражом, и занятыми клетками. Если стратегия «ближайшие узлы кратчайшим маршрутом» выигрывает большинство уровней, размена нет — остаётся Flow Free со счётчиком. Провал по критерию означает, что общий бюджет не создаёт решения: это свойство расстановки узлов относительно запаса, а не размера сетки.

# 2. Цель и условия

Правила уровня — текст для кнопки `?`:

Соединяй по два узла одного цвета. Сам выбирай, какие два узла одного цвета станут парой. Проводи кабель по свободным клеткам сетки: каждый пройденный сегмент тратит 1 единицу общего запаса. Проложенный кабель остаётся на поле и блокирует свои клетки для других кабелей. Соедини все узлы и не потрать больше кабеля, чем есть в мотке.

- Условие ПОБЕДЫ: все узлы объединены в пары того же цвета, каждый узел использован ровно один раз, и суммарная длина всех зафиксированных кабелей не превышает `cableBudget`.
- Условие ПОРАЖЕНИЯ: выполняется хотя бы одно из условий:
  - остаток кабеля стал меньше нуля;
  - на поле остались неиспользованные узлы, но не существует ни одного полного решения из текущего состояния в пределах оставшегося бюджета и свободных клеток.
- Если игрок рисует маршрут, который уже в момент подтверждения превышает остаток кабеля, такой маршрут не фиксируется и состояние не меняется.
- Runtime RNG отсутствует. Позиции узлов, цвет каждого узла, препятствия и бюджет заранее заданы уровнем.

# 3. Правила

1. На старте движок загружает фиксированную прямоугольную сетку.
2. На сетке размещены узлы нескольких цветов.
3. Для каждого цвета количество узлов всегда чётное: `2, 4, 6...`.
4. Пары внутри цвета заранее не назначены.
5. Каждый узел может участвовать ровно в одном соединении.
6. На старте также задан общий запас кабеля `cableBudget`.
7. Остаток кабеля равен `cableBudget - usedCable` и всегда виден игроку.
8. Кабель прокладывается только ортогонально по клеткам сетки.
9. Диагональные сегменты запрещены.
10. Кабель нельзя проводить через препятствия.
11. Кабель нельзя проводить через клетку, занятую другим уже зафиксированным кабелем.
12. Кабель нельзя проводить через чужой узел.
13. Через стартовый и конечный узлы текущего соединения маршрут проходить может только как через свои концы; использовать узел как промежуточную клетку нельзя.
14. Игрок начинает drag на свободном узле.
15. Во время drag renderer строит ортогональный маршрут по клеткам, engine валидирует каждую следующую клетку.
16. Маршрут можно завершить только на другом неиспользованном узле того же цвета.
17. Завершение на узле другого цвета невалидно.
18. Завершение на уже использованном узле невалидно.
19. Завершение в пустой клетке не фиксирует кабель.
20. Стоимость соединения равна количеству ортогональных сегментов между соседними клетками маршрута.
21. Во время рисования текущая стоимость маршрута показывается игроку в реальном времени.
22. Если стоимость маршрута превышает остаток кабеля, маршрут помечается невалидным и не может быть подтверждён.
23. После валидного отпускания на подходящем узле маршрут фиксируется.
24. Оба конечных узла помечаются использованными.
25. Зафиксированный кабель остаётся на поле до конца уровня.
26. Зафиксированный кабель занимает все клетки своего маршрута и блокирует их для следующих соединений.
27. Зафиксированные кабели нельзя пересекать, накладывать друг на друга или редактировать.
28. После фиксации соединения `usedCable` увеличивается на стоимость маршрута.
29. Автоматического выбора пары нет: выбор пары определяется двумя узлами, между которыми игрок протянул кабель.
30. Автоматического поиска кратчайшего пути нет: форма маршрута полностью задаётся жестом игрока.
31. После каждого валидного соединения движок проверяет победу.
32. Если все узлы использованы и бюджет не превышен, фиксируется `level_win`.
33. Если остались неиспользованные узлы, движок проверяет существование хотя бы одного полного решения из текущего состояния.
34. Если полного решения больше нет, фиксируется `level_fail` с причиной `dead_end`.
35. Все проверки детерминированы текущим состоянием поля; runtime RNG отсутствует.

# 5. Ввод

Игровой ввод:

```ts
{
  type: 'cable_drag_start';
  nodeId: string;
}
|
{
  type: 'cable_drag_step';
  x: number;
  y: number;
}
|
{
  type: 'cable_drag_end';
  nodeId: string | null;
}
```

- `cable_drag_start` возможен только на неиспользованном узле.
- `cable_drag_step` добавляет следующую ортогонально соседнюю клетку, если она валидна.
- Возврат drag на предыдущую клетку текущего незавершённого маршрута удаляет последний сегмент и уменьшает preview-стоимость на 1.
- `cable_drag_end` фиксирует маршрут только если конечный узел свободен и имеет тот же `colorId`.
- Engine повторно валидирует весь маршрут перед фиксацией.

# 6. Контент уровня

Пример `levels.json`:

```json
{
  "id": 1,
  "grid": { "w": 7, "h": 7 },
  "cableBudget": 24,
  "blockedCells": [
    { "x": 3, "y": 2 },
    { "x": 3, "y": 3 }
  ],
  "nodes": [
    { "id": "r1", "x": 0, "y": 0, "colorId": "red" },
    { "id": "r2", "x": 2, "y": 1, "colorId": "red" },
    { "id": "r3", "x": 5, "y": 0, "colorId": "red" },
    { "id": "r4", "x": 6, "y": 3, "colorId": "red" },
    { "id": "b1", "x": 1, "y": 5, "colorId": "blue" },
    { "id": "b2", "x": 5, "y": 6, "colorId": "blue" }
  ]
}
```

Правила генерации:

- Для каждого цвета количество узлов чётное.
- Рекомендуемый диапазон для прототипа: 2–3 цвета, 2–6 узлов на цвет, 6–12 узлов всего.
- Узлы и препятствия фиксированы до старта уровня.
- `cableBudget` задаётся заранее.
- Генератор обязан прогнать solver и подтвердить хотя бы одно полное решение.
- Solver должен оптимизировать одновременно:
  - разбиение узлов каждого цвета на пары;
  - маршруты между выбранными парами;
  - порядок фиксации кабелей;
  - суммарную длину;
  - отсутствие взаимных блокировок.
- Уровень не принимается, если жадная стратегия «ближайшая пара + кратчайший текущий маршрут» решает его без развилки.
- Уровень не принимается, если все решения требуют угадывать между визуально эквивалентными вариантами без читаемого пространственного основания.
- Уровень не принимается, если правильное решение использует весь бюджет с нулевым запасом на обучающих уровнях 1–2.
- Runtime RNG отсутствует.

Кривая по пяти уровням:

1. **Обучение бюджету.** 2 красных + 2 синих, без препятствий. Пары фактически очевидны; игрок понимает стоимость каждого сегмента и общий остаток кабеля.
2. **Первый выбор пары.** 4 красных + 2 синих. У красных есть два возможных естественных разбиения; одно заметно дороже.
3. **Первый настоящий выбор.** 4 красных + 4 жёлтых. Ближайшая красная пара перекрывает удобный коридор жёлтым; нужно выбрать менее очевидную пару или маршрут.
4. **Давление ресурса.** 3 цвета, 8–10 узлов, несколько препятствий. Есть как минимум один дешёвый маршрут, который создаёт `dead_end` для оставшихся узлов.
5. **Проверка концепта.** 10–12 узлов, включая цвет с 6 узлами. Игрок должен решить одновременно, как разбить этот цвет на 3 пары и как развести несколько кабелей в пределах жёсткого общего бюджета.

# 7. Визуал

- Поле: чистая квадратная сетка.
- Узел: круглый коннектор с хорошо читаемым цветом из `tokens.css`.
- Узлы одного цвета визуально одинаковы; никаких заранее показанных линий пары нет.
- Использованный узел остаётся виден как конец соответствующего кабеля.
- Препятствие: нейтральная непрозрачная клетка.
- Текущий незавершённый кабель рисуется поверх сетки с явным preview пути.
- Рядом с текущим маршрутом показывается его стоимость, например `−5`.
- HUD всегда показывает `Осталось кабеля: N`.
- При валидном соединении кабель коротко подсвечивается от начала к концу, оба узла дают `snap`/`pulse`, затем HUD уменьшает остаток — payoff должен читаться за ~1 секунду.
- Если игрок пытается провести кабель через занятую или запрещённую клетку, последний сегмент коротко дёргается/подсвечивается как невалидный, состояние не меняется.
- Если preview превышает остаток кабеля, линия переходит в error-state и значение стоимости показывает перерасход.
- При `dead_end` оставшиеся свободные узлы дают короткий общий импульс, а поле показывает, что больше полного решения нет.
- HUD помимо остатка кабеля: количество неиспользованных узлов `N`.

# 8. Онбординг

1. Соединяй два узла одного цвета.
2. Если узлов одного цвета больше двух, сам решай, какие из них станут парой.
3. Каждый сегмент пути тратит 1 кабель из общего запаса.
4. Проложенный кабель остаётся на поле и блокирует клетки.
5. Короткий путь экономит кабель, но может перекрыть дорогу остальным.
6. Соедини все узлы и не выйди за общий бюджет.

`?` повторяет только правила, без подсказки конкретного решения уровня.

# 10. Метрики и события

Аналитикой владеет общий shell. Механика **не вызывает PostHog напрямую** —
она сообщает о происходящем через контракт `MechanicHost`.

- Shell сам логирует `game_open`, `help_open`, `level_start`, `level_win`,
  `level_5_complete`, `rating_submit`, `comment_submit`.
- Hub отдельно логирует `hub_impression`, `hub_click`, `teaser_click`.
- D1/D7 и повторные сессии PostHog считает сам по persisted distinct_id и
  `game_open` — отдельные события для них не нужны.
- `retry` шлёт shell после fail-попапа; `level_5_complete` отдельно не
  эмитится, он выводится из `level_win` пятого уровня.

Ниже описано, **когда** наступает каждое событие. Механика при этом вызывает
только `onFirstAction()`, `onFail('<код>')` и `onComplete()` — остальное
отправляет shell.

- `first_action` — первый валидный `cable_drag_start` с последующим хотя бы одним валидным `cable_drag_step`;
- `level_start` — при входе на уровень;
- `level_win` — когда все узлы использованы и бюджет не превышен;
- `level_fail` — с `reason: 'dead_end'`, если из текущего состояния больше нет полного решения;
- `retry` — при повторной попытке того же уровня после fail.

Для каждого подтверждённого соединения в диагностическом payload можно хранить:

- `color_id`;
- `from_node_id`;
- `to_node_id`;
- `route_length`;
- `cable_remaining`;
- `unused_nodes_remaining`;
- `was_shortest_route_for_pair`;
- `was_nearest_same_color_pair`.

`level_5_complete` отдельно не эмитится: он автоматически следует из `level_win` пятого уровня.

Онлайн-гейты как резерв:

- **Readability:** игрок понимает без дополнительного обучения, что пары внутри цвета выбирает сам и что весь уровень делит один бюджет.
- **Reach L5:** достаточная доля игроков доходит до пятого уровня.
- **D1:** возврат на следующий день.

Если kill-критерий выполняется или онлайн-гейты провалены — концепт хоронится, а не чинится дополнительными системами.

# 11. Крайние случаи

- **Повторный drag с того же узла** — после фиксации оба конца помечены использованными (п.24), а начать drag можно только со свободного узла (п.14). Отредактировать проложенный кабель нельзя (п.27).
- **Drag мимо всего** — завершение в пустой клетке кабель не фиксирует (п.19); завершение на узле чужого цвета или уже использованном невалидно (п.17–18).
- **Действие невозможно** — маршрут дороже остатка подтвердить нельзя (п.22). Если ни одно валидное соединение больше не собирается — остатка не хватает ни на один маршрут или свободные узлы одного цвета уже отрезаны занятыми клетками, — фиксируется поражение немедленно. Правила 1–29 такой проверки не описывали, и без неё игрок оставался бы на поле без исхода.
- **Ходов не осталось, победа не выполнена** — неприменимо: ограничен кабель, а не ходы. Исчерпанный бюджет проявляется именно как отсутствие валидных маршрутов и обрабатывается предыдущим пунктом.
- **Два объекта в одной позиции** — неприменимо: клетка занята либо узлом, либо ровно одним зафиксированным кабелем; пересечения и наложения запрещены (п.11, 26–27).

# 12. Профиль реализации

Относится к фабрике, а не к игровой идее: сменится фабрика — перепишется
только этот раздел.

**Контракт.** Механика реализует `MechanicHost` из `src/shell-contract.ts` и
вызывает `onFirstAction()`, `onComplete()`, `onFail(reason)`, `onExit()`.
PostHog напрямую не трогает — см. раздел 10.

**`game.config.ts`.** `id` совпадает со `slug` из шапки, `title` — с
`title_ru`, `tagline` — короткая строка под названием, `levelCount: 5`,
`version` и `onboarding.version` поднимаются при изменении контента и правил
соответственно. Токены аналитики и ключ обратной связи копируются из
`games/tap-targets/game.config.ts`.

**`data-testid`.** Обязателен на каждом интерактивном элементе — e2e ищет
строго по ним. Существующая конвенция: `game-surface` — контейнер механики,
`mechanic-hud` — HUD с атрибутом `data-remaining`.

**Анимация.** Payoff строится из эффектов `render-kit`: `punch`,
`invalidShake`, `successFlash`, `fadeCollapse`, `cameraShake`, `moveTo`.
Если нужного нет — сказать здесь, а не изобретать свой во время сборки.
_Какие именно эффекты нужны этой игре — не записано._
