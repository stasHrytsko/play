# 1. Паспорт концепта

Дополнительно:
- Поле прототипа: 8×8.
- Все данные уровня фиксированы заранее. Runtime RNG отсутствует.

**Почему kill-критерий именно такой.** Идея в том, что отдельного действия «подождать» нет: единственные часы — собственное движение, поэтому выбирая, куда идти, игрок выбирает, когда всё созреет. Если жадная стратегия набирает почти оптимум на большинстве уровней, маршрут-как-таймер ни разу не заставляет выстраивать порядок — остаётся обычный сбор по пути. Провал по критерию означает, что твист не создаёт решения: это свойство того, как значения `ripeAt` разнесены относительно расстояний, а не размера поля.

# 2. Цель и условия

Правила уровня — текст для кнопки `?`:

На поле 8×8 есть игрок и плоды. Каждый плод имеет свой момент спелости. Один шаг на соседнюю клетку = один ход, поэтому после каждого шага все несобранные плоды становятся на один ход старше. Если зайти на клетку плода до его момента спелости, он даёт 2 очка. Если зайти ровно в момент спелости — 3 очка. Если позже — 1 очко. Плод собирается автоматически. Собери все плоды и постарайся набрать максимум очков.

- Условие ПОБЕДЫ: собраны все плоды уровня.
- Условие ПОРАЖЕНИЯ: отсутствует.
- Итог уровня: `score` из максимально возможного `optimalScore`, рассчитанного solver для конкретного уровня.
- Игрок всегда может продолжать движение, пока не собраны все плоды.
- Скрытой информации нет: положение плодов, их текущая стадия и число ходов до спелости видимы.

Точная шкала очков:

- `turn < ripeAt` → недозрелый → `+2`.
- `turn === ripeAt` → спелый → `+3`.
- `turn > ripeAt` → переспелый → `+1`.

`turn` начинается с `0`. Каждый валидный шаг игрока сначала увеличивает `turn` на `1`, затем движок проверяет плод на клетке назначения и начисляет очки по новому значению `turn`.

Пример: плод с `ripeAt: 3` в начале показывает `3`. Если игрок попадёт на него третьим шагом, получит 3 очка.

# 3. Правила

1. На старте движок загружает фиксированное поле 8×8, стартовую клетку игрока и фиксированный набор плодов.
2. Каждый плод занимает ровно одну клетку.
3. На одной клетке не может находиться более одного плода.
4. Стартовая клетка игрока не содержит плод.
5. У каждого плода заранее задан `ripeAt` — номер хода, на котором этот плод является спелым.
6. На старте `turn = 0`.
7. Игрок может сделать шаг только на одну ортогонально соседнюю клетку: вверх, вниз, влево или вправо.
8. Диагональные перемещения запрещены.
9. Выход за границы 8×8 запрещён; такой ввод ничего не меняет и не считается ходом.
10. Валидный шаг перемещает игрока на соседнюю клетку и увеличивает `turn` ровно на 1.
11. После увеличения `turn` движок пересчитывает визуальную стадию всех несобранных плодов относительно их `ripeAt`.
12. Если клетка назначения содержит несобранный плод, он собирается автоматически в этот же ход.
13. Если при сборе `turn < ripeAt`, плод даёт 2 очка.
14. Если при сборе `turn === ripeAt`, плод даёт 3 очка.
15. Если при сборе `turn > ripeAt`, плод даёт 1 очко.
16. После сбора плод удаляется с поля навсегда, а начисленные очки добавляются в `score`.
17. На пустую клетку можно заходить любое количество раз.
18. На клетку, где раньше был собран плод, можно заходить любое количество раз.
19. Отдельного действия `wait` нет: если игрок хочет потратить время, он должен реально двигаться по сетке.
20. Плоды не двигаются и не исчезают сами, даже если давно переспели.
21. Переспелый плод остаётся доступен и всегда стоит 1 очко независимо от того, насколько поздно его собрали.
22. Собранный плод не влияет на другие плоды кроме того, что путь до него уже потратил соответствующее число ходов.
23. Порядок сбора полностью выбирает игрок.
24. После каждого валидного шага движок проверяет условие завершения.
25. Когда собран последний плод, уровень немедленно заканчивается победой и показывает итоговый `score / optimalScore`.
26. Все последствия действий детерминированы текущим состоянием и данными уровня.

Вычисляемое состояние плода, отдельно хранить не обязательно:

```ts
type FruitStage = 'unripe' | 'ripe' | 'overripe';

function getFruitStage(fruit: Fruit, turn: number): FruitStage {
  if (turn < fruit.ripeAt) return 'unripe';
  if (turn === fruit.ripeAt) return 'ripe';
  return 'overripe';
```

# 5. Ввод

Один тип игрового ввода:

```ts
{
  type: 'move';
  dir: 'up' | 'down' | 'left' | 'right';
}
```

- Один `move` = максимум один шаг.
- Engine повторно валидирует границы поля.
- Невалидный `move` не меняет позицию и не увеличивает `turn`.
- `first_action` фиксируется на первом валидном `move`.

# 6. Контент уровня

Пример `levels.json`:

```json
{
  "id": 1,
  "grid": { "w": 8, "h": 8 },
  "playerStart": [3, 3],
  "fruits": [
    { "id": "a", "pos": [1, 2], "ripeAt": 3 },
    { "id": "b", "pos": [6, 2], "ripeAt": 5 },
    { "id": "c", "pos": [2, 6], "ripeAt": 7 },
    { "id": "d", "pos": [6, 6], "ripeAt": 9 }
  ]
}
```

`optimalScore` не обязан храниться в исходном JSON: он может вычисляться offline solver при сборке контента и сохраняться в скомпилированном уровне.

Требования к генератору:

- Поле прототипа всегда 8×8.
- В прототипе нет стен, телепортов, ускорителей и других типов клеток.
- Позиция игрока, позиции плодов и `ripeAt` фиксируются до запуска уровня.
- Runtime RNG отсутствует.
- Solver должен перебрать возможные порядки сбора и маршруты, включая осмысленные циклы для траты времени, и вернуть максимальный достижимый score.
- Уровень не принимается, если все плоды можно собрать спелыми без конфликта маршрутов.
- Уровень не принимается, если лучший маршрут совпадает с простым «всегда идти к ближайшему плоду» и нет хотя бы одной содержательной альтернативы.
- На уровнях 3–5 должен существовать хотя бы один локально привлекательный выбор, который уменьшает итоговый score по сравнению с оптимальным маршрутом.
- На уровне 5 оптимальный маршрут должен хотя бы один раз требовать сознательно собрать плод недозрелым за 2, чтобы сохранить более выгодный тайминг других плодов.

Кривая по пяти уровням:

1. **Обучение.** 3 плода. Один очевидно можно взять ровно спелым; игрок понимает, что каждый шаг меняет таймеры всех остальных.
2. **Первый конфликт.** 4 плода. Два плода имеют близкие `ripeAt`, и оба идеально собрать уже нельзя — приходится выбирать порядок.
3. **Первый настоящий маршрут.** 5 плодов в разных частях поля. Ближайший плод не обязательно лучший следующий выбор.
4. **Давление.** 6 плодов. Несколько окон спелости перекрываются; выгодный маршрут требует смотреть на 2–3 цели вперёд.
5. **Проверка концепта.** 7–8 плодов. Оптимум требует хотя бы одной осознанной жертвы: взять один плод недозрелым за 2 или оставить другой переспеть до 1 ради более высокого общего score.

# 7. Визуал

- Поле: квадратная сетка 8×8.
- Игрок: один простой блок/персонаж, визуально отличный от плодов.
- Каждый плод занимает одну клетку.
- У плода три ясно различимые визуальные стадии: недозрелый / спелый / переспелый. Конкретные цвета берутся из `tokens.css`, механика не зависит от цвета.
- Недозрелый плод показывает компактное число `N` — сколько ходов осталось до спелости.
- Спелый плод показывает явный payoff-state: короткий пульс/блик примерно на 1 секунду и значение `3` при сборе.
- Переспелый плод визуально «увядает», но остаётся хорошо читаемым и доступным.
- При сборе над клеткой на ~1 секунду появляется `+2`, `+3` или `+1`.
- Движение игрока между клетками коротко анимируется, но логическое состояние меняется сразу после валидного input.
- В верхней части экрана постоянно видна шкала ценности: `Недозрелый 2 · Спелый 3 · Переспелый 1`.
- HUD: текущий `score`, количество оставшихся плодов, текущий номер хода.
- После последнего плода показывается `Счёт: N / максимум M`.

# 8. Онбординг

1. Свайп/стрелка двигает игрока на одну клетку по вертикали или горизонтали.
2. Каждый шаг = один ход для всех плодов.
3. Число на плоде показывает, через сколько ходов он станет спелым.
4. Зайди на плод — он собирается автоматически.
5. Недозрелый = 2, спелый = 3, переспелый = 1.
6. Собери все плоды и набери как можно больше.

Кнопка `?` показывает только краткие правила из раздела 2, без пошагового обучения и без подсказки оптимального маршрута.

# 9. Явно ВНЕ рамок

- Без меты, валют, коллекций, заданий, ежедневных бонусов, рекламы, IAP.
- Без runtime RNG.
- Максимум одно давление: время созревания.
- Максимум один твист: каждый шаг по маршруту одновременно двигает глобальное время.
- Без изменений баланса/уровней после публикации; только датированный критический bugfix.

- Нет стен и препятствий в первом прототипе.
- Нет разных типов плодов с разными базовыми ценами: шкала 2 / 3 / 1 одинакова для всех.
- Нет бонусов за цепочки, комбо, скорость ввода или длину маршрута.
- Нет штрафа за сам факт лишнего шага кроме изменения времени созревания.
- Нет исчезновения переспелых плодов.

# 10. Метрики и события

Аналитикой владеет общий shell. Механика **не вызывает PostHog напрямую** —
она сообщает о происходящем через контракт `MechanicHost`.

- Shell сам логирует `game_open`, `help_open`, `level_start`, `level_win`,
  `level_5_complete`, `rating_submit`, `comment_submit`.
- Hub отдельно логирует `hub_impression`, `hub_click`, `teaser_click`.
- D1/D7 и повторные сессии PostHog считает сам по persisted distinct_id и
  `game_open` — отдельные события для них не нужны.
- `retry` шлёт shell после fail-попапа; `level_5_complete` отдельно не
  эмитится, он выводится из `level_win` пятого уровня.

Ниже описано, **когда** наступает каждое событие. Механика при этом вызывает
только `onFirstAction()`, `onFail('<код>')` и `onComplete()` — остальное
отправляет shell.

- `first_action` — первый валидный `move`, который реально переместил игрока.
- `level_start` — при входе на каждый уровень, параметр `level`.
- `level_win` — сразу после сбора последнего плода. Дополнительные поля: `score`, `optimal_score`, `turns`, `fruit_count`, `ripe_collected`, `unripe_collected`, `overripe_collected`.
- `retry` — если игрок вручную перезапускает уже начатый уровень; так как fail-state отсутствует, это не retry после `level_fail`, а restart текущего уровня. Если общий аналитический контракт допускает только retry после fail, отдельный event не эмитить и оставить restart на shell.
- `level_fail` — не используется: проигрыша в механике нет.
- `level_5_complete` — отдельно не эмитить; фиксируется автоматически как `level_win` пятого уровня.

Дополнительные mechanic events для диагностики прототипа:

- `fruit_collect` — `fruit_id`, `turn`, `ripe_at`, `stage`, `points`.
- `level_restart` — если поддерживается общим аналитическим слоем, `level`, `turn`, `score`, `remaining_fruits`.

Ключевые показатели теста:

- Средний `score / optimalScore` по каждому уровню.
- Доля игроков, которые на уровнях 3–5 меняют очевидный ближайший маршрут ради тайминга.
- Распределение собранных плодов по стадиям `unripe / ripe / overripe`.
- Число лишних шагов относительно кратчайшего маршрута, чтобы понять, используют ли игроки движение как осознанный инструмент тайминга.

Онлайн-ворота эксперимента остаются стандартными: читаемость правила, доходимость до 5 уровня, возврат D1.

Если kill-критерий из раздела 1 срабатывает, концепт хоронится, а не чинится добавлением стен, бустеров или новых типов плодов.

# 11. Крайние случаи

- **Повторный шаг в ту же сторону** — обычный ход. На пустую клетку и на клетку уже собранного плода заходить можно сколько угодно (п.17–18) — это единственный способ потратить время, отдельного `wait` нет (п.19).
- **Шаг мимо всего** — выход за границы 8×8 ничего не меняет и ходом не считается (п.9).
- **Действие невозможно** — не возникает: клетки не исчезают и не блокируются (п.20), поэтому хотя бы одна соседняя клетка доступна всегда. Единственное запрещённое направление — за границу поля.
- **Ходов не осталось, победа не выполнена** — неприменимо, и это стоит сказать прямо: **проиграть здесь нельзя.** Лимита ходов нет, переспелый плод остаётся доступен и всегда даёт 1 очко (п.21), уровень заканчивается сбором последнего плода (п.25). Давление создаёт не риск поражения, а разрыв между `score` и `optimalScore`.
- **Два объекта в одной позиции** — на клетке не более одного плода (п.3), стартовая клетка плода не содержит (п.4). Игрок и плод совмещаются ровно на один ход: плод собирается автоматически в момент входа (п.12) и удаляется навсегда (п.16).

# 12. Профиль реализации

Относится к фабрике, а не к игровой идее: сменится фабрика — перепишется
только этот раздел.

**Контракт.** Механика реализует `MechanicHost` из `src/shell-contract.ts` и
вызывает `onFirstAction()`, `onComplete()`, `onFail(reason)`, `onExit()`.
PostHog напрямую не трогает — см. раздел 10.

**`game.config.ts`.** `id` совпадает со `slug` из шапки, `title` — с
`title_ru`, `tagline` — короткая строка под названием, `levelCount: 5`,
`version` и `onboarding.version` поднимаются при изменении контента и правил
соответственно. Токены аналитики и ключ обратной связи копируются из
`games/tap-targets/game.config.ts`.

**`data-testid`.** Обязателен на каждом интерактивном элементе — e2e ищет
строго по ним. Существующая конвенция: `game-surface` — контейнер механики,
`mechanic-hud` — HUD с атрибутом `data-remaining`.

**Анимация.** Payoff строится из эффектов `render-kit`: `punch`,
`invalidShake`, `successFlash`, `fadeCollapse`, `cameraShake`, `moveTo`.
Если нужного нет — сказать здесь, а не изобретать свой во время сборки.
_Какие именно эффекты нужны этой игре — не записано._
