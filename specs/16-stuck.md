# 1. Паспорт концепта

Поля паспорта — в шапке раздела 0.

**Почему kill-критерий именно такой.** Идея в том, что запас действий принадлежит плитке, а не игроку: обмен — это выбор, какую из двух плиток потратить. Если оптимально почти всегда двигать те, у кого остаток больше, выбора нет — счётчик становится украшением, и остаётся обычный match-3. Провал по критерию означает, что индивидуальный запас не создаёт решения: это свойство идеи, потому что доминирование жадного правила не зависит от размера поля.

# 2. Цель и условия

Правила уровня — текст для кнопки `?`:

Меняй местами две соседние плитки, чтобы собирать три одинаковых в ряд. На каждой плитке видно, сколько действий у неё осталось. Успешный обмен уменьшает счётчик обеих плиток на 1. Плитка с `0` больше не может двигаться, но всё ещё может исчезнуть в совпадении. Очисти всё поле.

- Условие ПОБЕДЫ: на поле не осталось плиток.
- Условие ПОРАЖЕНИЯ: на поле остались плитки, но не существует ни одного валидного swap между двумя соседними плитками с `actionsLeft > 0`, который создаёт хотя бы одну тройку.
- Runtime RNG отсутствует. Начальная раскладка, цвета плиток и их `actionsLeft` заранее зафиксированы уровнем.

# 3. Правила

1. На старте движок загружает конечное поле цветных плиток. Новые плитки во время уровня не создаются.
2. У каждой плитки есть цвет и `actionsLeft` — целое число `0..3`.
3. Игрок выбирает две соседние по стороне плитки.
4. Swap возможен только если у обеих плиток `actionsLeft > 0`.
5. Движок временно меняет выбранные плитки местами и проверяет поле на совпадения.
6. Совпадение — минимум три плитки одного цвета подряд по горизонтали или вертикали.
7. Swap считается валидным, только если после него появилось хотя бы одно новое совпадение, в которое входит хотя бы одна из двух перемещённых плиток.
8. Если swap невалиден, плитки возвращаются на исходные места; действия не тратятся.
9. Если swap валиден, у обеих перемещённых плиток `actionsLeft` уменьшается на `1`.
10. Сначала применяется расход действий, затем разрешаются все совпадения текущего состояния поля.
11. Любая плитка, входящая хотя бы в одно совпадение, удаляется независимо от её текущего `actionsLeft`.
12. Поэтому плитка может потратить своё последнее действие, получить `0` и всё равно исчезнуть в созданной этим swap тройке.
13. Если плитка после успешного swap получила `0`, но не была удалена совпадением, она остаётся на поле и больше не может участвовать в будущих swap.
14. После удаления совпавших плиток все оставшиеся плитки в каждом столбце падают вертикально вниз до ближайшей свободной клетки.
15. Падение не расходует `actionsLeft`, потому что не является действием игрока.
16. После падения движок снова проверяет поле на совпадения.
17. Если появились автоматические совпадения, они удаляются, после чего снова применяется падение.
18. Каскад повторяется до стабильного состояния, в котором совпадений нет.
19. Автоматические удаления и падения не расходуют действия плиток.
20. После стабилизации, если плиток не осталось, фиксируется победа.
21. Если плитки остались, движок ищет хотя бы один валидный swap по правилам 3–8.
22. Если валидного swap нет, фиксируется поражение.
23. Если валидный swap есть, уровень продолжается.

# 4. Состояние уровня

```ts
type TileState = {
  id: string;
  x: number;
  y: number;
  color: string;
  actionsLeft: 0 | 1 | 2 | 3;
};

type GameState = {
  width: number;
  height: number;
  tiles: TileState[];
  moves: number;
  status: 'playing' | 'won' | 'failed';
};
```

Пустая клетка определяется отсутствием плитки в координате.

# 5. Ввод

Один тип игрового ввода — swap двух соседних плиток:

```ts
{
  type: 'swap';
  firstId: string;
  secondId: string;
}
```

Renderer может получить этот ввод через drag плитки на соседнюю или через tap по первой и второй плитке, но engine получает только `swap`.

# 6. Контент уровня

Пример `levels.json`:

```json
{
  "id": 1,
  "grid": { "w": 5, "h": 6 },
  "tiles": [
    { "x": 0, "y": 0, "color": "a", "actionsLeft": 2 },
    { "x": 1, "y": 0, "color": "b", "actionsLeft": 1 },
    { "x": 2, "y": 0, "color": "a", "actionsLeft": 2 }
  ]
}
```

Правила контента:
- На старте уровня не должно быть уже готовых совпадений.
- Рекомендуемый диапазон `actionsLeft`: `1–3`; `0` допустим только на более поздних уровнях как заранее неподвижная плитка.
- Генератор обязан прогнать solver и подтвердить, что поле можно полностью очистить.
- Solver обязан учитывать расход действий у обеих плиток при каждом swap, каскады и последующую гравитацию.
- Runtime RNG отсутствует.

Кривая по пяти уровням:

1. **Обучение ресурсу.** Поле небольшое; почти все плитки имеют `2–3` действия. Один очевидный swap показывает, что число на обеих плитках уменьшается.
2. **Первый ноль.** Есть плитка с `1`, которую нужно использовать ровно один раз; после swap она либо исчезает в match, либо остаётся неподвижной.
3. **Первый настоящий выбор.** Два разных валидных swap. Один даёт быстрый match, но тратит ресурс плитки, которая понадобится позже; второй сохраняет её.
4. **Давление.** Несколько плиток с `1`; минимум один очевидный локальный match делает уровень нерешаемым из-за потери подвижности позже.
5. **Проверка концепта.** Несколько последовательных развилок. Решение требует читать остаток действий на конкретных плитках, а стратегия «всегда двигай самую свежую плитку» не должна стабильно выигрывать.

# 7. Визуал

- Поле: прямоугольная сетка.
- Плитка: простая форма с цветом из `tokens.css` и крупным числом `actionsLeft` в центре или углу.
- `2 → 1 → 0` должно читаться мгновенно после успешного swap.
- Плитка с `0` визуально остаётся того же цвета, но получает состояние неподвижности: приглушённый контур/иконка замка без смены игрового цвета.
- Невалидный swap: короткий сдвиг и возврат, счётчики не меняются.
- Валидный swap: плитки меняются местами, числа уменьшаются, затем совпадение схлопывается.
- Каскад: после удаления плитки сверху быстро падают вниз; цепочка должна читаться без отдельной паузы между каждым шагом.
- Главный payoff: match удаляет плитки, особенно приятно когда плитка с `0` исчезает благодаря соседям.
- Ошибка/поражение: оставшиеся плитки с `0` и отсутствие доступных swap должны быть визуально очевидны за ~1 секунду.
- HUD: `Осталось: N`, `Ходы: M`.

# 8. Онбординг

1. Поменяй две соседние плитки, чтобы собрать три одинаковых.
2. У каждой плитки есть свой запас действий.
3. Успешный swap тратит по `1` у обеих плиток.
4. Плитка с `0` больше не двигается.
5. Но плитка с `0` всё ещё исчезает, если попала в тройку.
6. Очисти всё поле, пока остаются возможные обмены.

Кнопка `?` повторяет только краткие правила из раздела 2 и не запускает отдельный tutorial-flow.

# 10. Метрики и события

Аналитикой владеет общий shell. Механика **не вызывает PostHog напрямую** —
она сообщает о происходящем через контракт `MechanicHost`.

- Shell сам логирует `game_open`, `help_open`, `level_start`, `level_win`,
  `level_5_complete`, `rating_submit`, `comment_submit`.
- Hub отдельно логирует `hub_impression`, `hub_click`, `teaser_click`.
- D1/D7 и повторные сессии PostHog считает сам по persisted distinct_id и
  `game_open` — отдельные события для них не нужны.
- `retry` шлёт shell после fail-попапа; `level_5_complete` отдельно не
  эмитится, он выводится из `level_win` пятого уровня.

Ниже описано, **когда** наступает каждое событие. Механика при этом вызывает
только `onFirstAction()`, `onFail('<код>')` и `onComplete()` — остальное
отправляет shell.

- `first_action` — первый валидный swap;
- `level_start`;
- `level_win`;
- `level_fail` с `reason: 'no_valid_swap'`;
- `retry`.

Полезные поля механики:
- `moves`;
- `tiles_remaining`;
- `zero_action_tiles_remaining`;
- `avg_actions_left`;
- `cascade_count`;
- `max_cascade_depth`.

`level_5_complete` отдельно не вызывается: достижение считается по `level_win` для уровня 5.

Онлайн-гейты в резерве:
- читается ли правило индивидуального ресурса без объяснения;
- доходит ли игрок до L5;
- D1.

Kill-критерий после тестов:
- если победные траектории в основном сводятся к выбору плитки с максимальным `actionsLeft`, а конкретная структура поля и будущая нужность плиток почти не влияют на решения, концепт хоронится, а не балансируется после публикации.

# 11. Крайние случаи

- **Обратный swap тех же двух плиток** — возможен, только если он сам создаёт новое совпадение (п.7); иначе невалиден, плитки возвращаются и действия не тратятся (п.8). Отменить ход обменом назад нельзя — обратный обмен почти никогда не легален.
- **Выбор мимо всего** — две несоседние плитки или пустое место — действие не выполняется, `actionsLeft` не тратится.
- **Действие невозможно** — swap запрещён, если хотя бы у одной из двух плиток `actionsLeft === 0` (п.4). Плитка с нулём остаётся на поле и может исчезнуть в чужом совпадении (п.11–13). Если валидного swap нет вовсе, фиксируется поражение (п.21–22).
- **Ходов не осталось, победа не выполнена** — общего лимита ходов нет — запас индивидуален. Исчерпание запаса у всех плиток проявляется как отсутствие валидного swap и обрабатывается п.22.
- **Два объекта в одной позиции** — неприменимо: обмен атомарен (п.5), при невалидном плитки возвращаются (п.8), а падение идёт до ближайшей свободной клетки (п.14).

# 12. Профиль реализации

Относится к фабрике, а не к игровой идее: сменится фабрика — перепишется
только этот раздел.

**Контракт.** Механика реализует `MechanicHost` из `src/shell-contract.ts` и
вызывает `onFirstAction()`, `onComplete()`, `onFail(reason)`, `onExit()`.
PostHog напрямую не трогает — см. раздел 10.

**`game.config.ts`.** `id` совпадает со `slug` из шапки, `title` — с
`title_ru`, `tagline` — короткая строка под названием, `levelCount: 5`,
`version` и `onboarding.version` поднимаются при изменении контента и правил
соответственно. Токены аналитики и ключ обратной связи копируются из
`games/tap-targets/game.config.ts`.

**`data-testid`.** Обязателен на каждом интерактивном элементе — e2e ищет
строго по ним. Существующая конвенция: `game-surface` — контейнер механики,
`mechanic-hud` — HUD с атрибутом `data-remaining`.

**Анимация.** Payoff строится из эффектов `render-kit`: `punch`,
`invalidShake`, `successFlash`, `fadeCollapse`, `cameraShake`, `moveTo`.
Если нужного нет — сказать здесь, а не изобретать свой во время сборки.
_Какие именно эффекты нужны этой игре — не записано._
