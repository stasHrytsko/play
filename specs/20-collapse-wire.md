# 1. Паспорт концепта

Поля паспорта — в шапке раздела 0.

**Почему kill-критерий именно такой.** Идея в том, что поле перестраивается после каждого соединения: какую пару соединить первой — значит выбрать, какое поле увидишь следующим. Если порядок не влияет на решаемость большинства уровней, перестройка — украшение, а игра остаётся обычным Flow Free. Провал по критерию означает, что твист не кусается: это свойство того, как расписана перестройка относительно раскладки точек, то есть самой идеи, а не размера сетки.

# 2. Цель и условия

Правила уровня — текст для кнопки `?`:

Соедини две точки одного цвета проводом через свободные клетки. Провод нельзя проводить через другие точки. Когда пара соединена, обе точки и провод исчезают. После этого каждая оставшаяся точка пытается сдвинуться ровно на одну соседнюю клетку. Сдвиги заранее заданы уровнем: при повторе всё происходит одинаково. Соедини все пары.

- Условие ПОБЕДЫ: на поле не осталось точек.
- Условие ПОРАЖЕНИЯ: точки ещё остались, но ни для одной пары одинакового цвета не существует пути между её двумя точками через свободные клетки.
- Runtime RNG отсутствует. Начальное поле и вся последовательность перестроений после 1-го, 2-го, 3-го и последующих успешных соединений заранее зафиксированы уровнем.

# 3. Правила

1. На старте движок загружает прямоугольную сетку и чётное количество точек; каждый цвет представлен ровно двумя точками.
2. Одна клетка может содержать не более одной точки.
3. Игрок начинает жест на точке.
4. Во время удержания пальца провод продолжается по ортогонально соседним клеткам: вверх, вниз, влево или вправо.
5. Провод нельзя проводить по диагонали.
6. Провод нельзя проводить через клетку, занятую любой другой точкой.
7. Провод нельзя повторно провести через клетку уже текущего пути.
8. Провод можно завершить только на второй точке того же цвета, с которой начат жест.
9. Если игрок отпускает палец до правильной второй точки, провод отменяется; состояние поля не меняется.
10. Невалидный жест ничего не меняет и не запускает перестройку.
11. Успешный провод соединяет пару.
12. Сразу после успешного соединения обе точки этой пары удаляются.
13. Сам провод также удаляется; его клетки снова становятся свободными.
14. После удаления пары начинается ровно одна фаза перестройки.
15. Для каждой фазы перестройки уровень заранее хранит порядок обработки оставшихся точек и желаемое направление сдвига каждой из них.
16. Каждая оставшаяся точка обрабатывается не более одного раза за эту фазу.
17. Точка пытается сдвинуться ровно на одну клетку в заданном направлении: `up`, `down`, `left` или `right`.
18. Если целевая клетка находится за границей поля или занята в момент обработки, точка остаётся на месте.
19. Если целевая клетка свободна, точка перемещается в неё.
20. Точки обрабатываются последовательно в заранее заданном `moveOrder`; поэтому конфликт двух точек за одну клетку всегда разрешается одинаково.
21. После обработки всех оставшихся точек фаза перестройки заканчивается.
22. После перестройки движок проверяет условие победы.
23. Если победы нет, движок проверяет существование хотя бы одной соединяемой пары.
24. Пара считается соединяемой, если между двумя её точками существует ортогональный путь через свободные клетки.
25. Если ни одной соединяемой пары нет, фиксируется поражение.
26. Если соединяемая пара есть, игрок делает следующий жест.
27. Никакие точки не создаются заново и не меняют цвет.

# 4. Состояние уровня

```ts
type Dir = 'up' | 'down' | 'left' | 'right';

type PointState = {
  id: string;
  pairId: string;
  x: number;
  y: number;
};

type ShiftInstruction = {
  pointId: string;
  dir: Dir;
};

type ReshuffleStep = {
  moveOrder: ShiftInstruction[];
};

type GameState = {
  points: PointState[];
  connectionIndex: number;
  activePath: { x: number; y: number }[];
  status: 'playing' | 'won' | 'failed';
};
```

`connectionIndex` равен количеству уже успешно соединённых пар и выбирает следующую запись `reshuffles[connectionIndex]` из контента уровня.

# 5. Ввод

Один тип игрового ввода — непрерывное проведение провода:

```ts
{
  type: 'connect';
  fromPointId: string;
  path: { x: number; y: number }[];
  toPointId: string;
}
```

Renderer может собирать `path` во время drag, но engine принимает результат как один жест. Один завершённый валидный провод = одно игровое действие.

# 6. Контент уровня

Пример `levels.json`:

```json
{
  "id": 1,
  "grid": { "w": 6, "h": 6 },
  "points": [
    { "id": "r1", "pairId": "red", "x": 0, "y": 0 },
    { "id": "r2", "pairId": "red", "x": 5, "y": 5 },
    { "id": "b1", "pairId": "blue", "x": 1, "y": 2 },
    { "id": "b2", "pairId": "blue", "x": 0, "y": 5 },
    { "id": "g1", "pairId": "green", "x": 3, "y": 0 },
    { "id": "g2", "pairId": "green", "x": 4, "y": 4 }
  ],
  "reshuffles": [
    {
      "moveOrder": [
        { "pointId": "b1", "dir": "down" },
        { "pointId": "g1", "dir": "left" },
        { "pointId": "b2", "dir": "right" },
        { "pointId": "g2", "dir": "up" }
      ]
    },
    {
      "moveOrder": [
        { "pointId": "g1", "dir": "down" },
        { "pointId": "g2", "dir": "left" }
      ]
    }
  ]
}
```

Правила контента:

- Количество `reshuffles` должно быть не меньше `pairCount - 1`.
- Инструкции для уже удалённых точек игнорируются.
- Для каждой ещё существующей точки в текущей фазе допускается максимум одна инструкция движения.
- Все инструкции движения заданы заранее и не генерируются во время игры.
- Генератор обязан прогнать solver и подтвердить хотя бы один порядок соединений, который приводит к победе.
- Solver обязан сравнивать разные порядки пар и отбрасывать уровни, где порядок практически не влияет на достижимость.

Кривая по пяти уровням:

1. **Обучение соединению.** 2 пары на просторном поле. После первой пары оставшиеся две точки сдвигаются на один очевидный шаг, но остаются соединяемыми.
2. **Обучение перестройке.** 3 пары. После первого соединения одна пара становится проще, другая — сложнее. Игрок видит, что поле нужно перечитывать после каждого схлопывания.
3. **Первый настоящий выбор.** 4 пары. В начале доступны минимум две пары, но только один из первых выборов сохраняет удобный маршрут для следующей пары после перестройки.
4. **Давление места.** 5 пар на более тесной сетке. Не меньше двух перестроек меняют соединяемость пар; один очевидный ранний выбор приводит к тупику позже.
5. **Проверка концепта.** 6 пар. В начале доступны минимум три пары. Есть минимум три решения вида «соединить сейчас или оставить на потом», и хотя бы один неверный порядок приводит к состоянию без доступных пар до очистки поля.

# 7. Визуал

- Поле: квадратная или прямоугольная клеточная сетка.
- Точки: простые круглые узлы; цвет берётся только из `tokens.css`.
- Каждая пара визуально различается цветом; дополнительных символов в базовом прототипе не требуется.
- Активный провод: толстая линия по центрам клеток с прямыми 90° поворотами.
- Во время drag путь подсвечивается сразу.
- Невалидная клетка кратко показывает ошибку, но не меняет состояние.
- Успешное соединение: оба узла стягиваются по проводу и исчезают вместе с ним примерно за `250–400 ms`.
- После исчезновения запускается перестройка: оставшиеся точки одновременно визуально начинают движение, но финальные позиции соответствуют последовательной детерминированной обработке движком.
- Каждая точка перемещается максимум на одну клетку за одну перестройку.
- Главный payoff должен читаться примерно за секунду: `соединил → пара исчезла → поле перестроилось`.
- HUD: `Пар осталось: N`.

# 8. Онбординг

1. Соедини две точки одного цвета.
2. Веди провод только через свободные клетки.
3. Соединённая пара и провод исчезают.
4. После этого остальные точки сдвигаются на одну соседнюю клетку.
5. Поле каждый раз перестраивается — ищи новую доступную пару.
6. Убери все пары.

Кнопка `?` показывает правила уровня, но не подсвечивает решение и не предлагает конкретную пару.

# 10. Метрики и события

Аналитикой владеет общий shell. Механика **не вызывает PostHog напрямую** —
она сообщает о происходящем через контракт `MechanicHost`.

- Shell сам логирует `game_open`, `help_open`, `level_start`, `level_win`,
  `level_5_complete`, `rating_submit`, `comment_submit`.
- Hub отдельно логирует `hub_impression`, `hub_click`, `teaser_click`.
- D1/D7 и повторные сессии PostHog считает сам по persisted distinct_id и
  `game_open` — отдельные события для них не нужны.
- `retry` шлёт shell после fail-попапа; `level_5_complete` отдельно не
  эмитится, он выводится из `level_win` пятого уровня.

Ниже описано, **когда** наступает каждое событие. Механика при этом вызывает
только `onFirstAction()`, `onFail('<код>')` и `onComplete()` — остальное
отправляет shell.

- `first_action` — первый валидно завершённый провод;
- `level_start`;
- `level_win`;
- `level_fail` с `reason = no_connectable_pairs`;
- `retry`.

Дополнительные диагностические поля на успешном соединении:

- `pair_id`;
- `connection_index`;
- `path_length`;
- `movable_pairs_before`;
- `movable_pairs_after`;
- `points_moved`.

`level_5_complete` отдельно не эмитится: определяется по `level_win` для уровня 5.

Онлайн-гейты в резерве:

- читаемость: игрок понимает связь `соединение → исчезновение → перестройка` без текста после первого уровня;
- достижение L5;
- D1.

Если kill-критерий подтверждается — концепт закрывается, а не чинится усложнением уровней.

# 11. Крайние случаи

- **Повторный жест по тому же пути** — после успешного соединения обе точки пары удалены (п.12), повторять нечего. Повторный незавершённый жест ничего не меняет и перестройку не запускает (п.9–10).
- **Жест мимо всего** — жест начинается только на точке (п.3); проведённый с пустой клетки он не начинается вовсе.
- **Действие невозможно** — если ни одной соединяемой пары нет — то есть ни для одной пары не существует ортогонального пути через свободные клетки, — фиксируется поражение (п.23–25). Проверка идёт после каждой перестройки, а не по запросу игрока.
- **Ходов не осталось, победа не выполнена** — неприменимо: лимита ходов нет, конец уровня определяется отсутствием соединяемых пар.
- **Два объекта в одной позиции** — клетка содержит не более одной точки (п.2). Конфликт двух точек за одну клетку во время перестройки разрешается детерминированно: точки обрабатываются в заранее заданном `moveOrder`, и опоздавшая остаётся на месте (п.18, 20).

# 12. Профиль реализации

Относится к фабрике, а не к игровой идее: сменится фабрика — перепишется
только этот раздел.

**Контракт.** Механика реализует `MechanicHost` из `src/shell-contract.ts` и
вызывает `onFirstAction()`, `onComplete()`, `onFail(reason)`, `onExit()`.
PostHog напрямую не трогает — см. раздел 10.

**`game.config.ts`.** `id` совпадает со `slug` из шапки, `title` — с
`title_ru`, `tagline` — короткая строка под названием, `levelCount: 5`,
`version` и `onboarding.version` поднимаются при изменении контента и правил
соответственно. Токены аналитики и ключ обратной связи копируются из
`games/tap-targets/game.config.ts`.

**`data-testid`.** Обязателен на каждом интерактивном элементе — e2e ищет
строго по ним. Существующая конвенция: `game-surface` — контейнер механики,
`mechanic-hud` — HUD с атрибутом `data-remaining`.

**Анимация.** Payoff строится из эффектов `render-kit`: `punch`,
`invalidShake`, `successFlash`, `fadeCollapse`, `cameraShake`, `moveTo`.
Если нужного нет — сказать здесь, а не изобретать свой во время сборки.
_Какие именно эффекты нужны этой игре — не записано._
