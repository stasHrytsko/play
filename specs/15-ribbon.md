# 2. Цель и условия

Правила уровня — текст для кнопки `?`:

Каждая цветная полоска равна `100%`. Внизу показаны открытые заказы: какой цвет и какой процент нужен в корзину. Нажми на полоску в месте разреза. Разрез делит её на два куска, сумма которых всегда `100%`. Каждый кусок, который точно совпадает с открытым заказом этого цвета, автоматически уходит в корзину. Ненужные куски уходят в отходы. После разреза приезжает следующая полоска. Следующие 3 цвета видны заранее.

- Условие ПОБЕДЫ: все компоненты всех заказов выполнены до того, как закончилась фиксированная очередь полосок.
- Условие ПОРАЖЕНИЯ: очередь полосок закончилась, а хотя бы один компонент заказа не выполнен.
- Других условий поражения нет.
- Runtime RNG отсутствует. Очередь цветов и список заказов заранее зафиксированы уровнем.

Проценты в прототипе кратны `5%`. Допустимые точки разреза: `5, 10, 15, ... 95`.

# 3. Правила

1. На старте уровень загружает фиксированную очередь полосок и фиксированный список заказов.
2. Каждая новая полоска приходит в рабочую зону с длиной `100%` и одним заданным цветом.
3. Игрок видит текущую полоску и цвета следующих 3 полосок в очереди.
4. Внизу одновременно видны все ещё не выполненные компоненты заказов.
5. Один компонент заказа задаётся парой `цвет + процент`, например `зелёный 25%`.
6. Один заказ может состоять из одного или нескольких компонентов разных цветов.
7. Игрок тапает по текущей полоске в точке предполагаемого разреза.
8. Рендерер переводит координату тапа в ближайшее значение, кратное `5%`.
9. Значения `0%` и `100%` недопустимы; такой тап ничего не делает.
10. Валидный тап делит полоску ровно на два куска: `cutPercent` и `100 - cutPercent`.
11. После разреза движок обрабатывает первый кусок, затем второй.
12. Для каждого куска движок ищет самый старый невыполненный компонент заказа с тем же цветом и тем же процентом.
13. Если совпадение найдено, кусок автоматически отправляется в соответствующую корзину, а компонент помечается выполненным.
14. Если совпадения нет, кусок отправляется в отходы.
15. Один кусок может выполнить только один компонент заказа.
16. Если два компонента полностью одинаковы, куски заполняют их по порядку отображения заказов сверху вниз.
17. Если оба куска совпадают с двумя открытыми компонентами, оба компонента закрываются одним разрезом.
18. Пример: зелёная полоска, открыты `зелёный 75%` и `зелёный 25%`; разрез на `75%` закрывает оба компонента.
19. Пример: синяя полоска, открыт только `синий 60%`; разрез на `60%` отправляет `60%` в заказ, а `40%` — в отходы.
20. После обработки обоих кусков текущая полоска удаляется с конвейера.
21. Следующая полоска очереди становится текущей, preview сдвигается на одну позицию.
22. Один валидный разрез считается одним ходом.
23. Игрок не может вернуть уже разрезанную полоску, склеить куски или изменить выполненный заказ.
24. Игрок не может переставлять очередь полосок.
25. Игрок не может пропустить текущую полоску без разреза.
26. Если после обработки кусков все компоненты выполнены, фиксируется победа по п.2.
27. Если очередь закончилась и невыполненные компоненты остались, фиксируется поражение по п.2.

# 6. Контент уровня

Пример `levels.json`:

```json
{
  "id": 1,
  "previewCount": 3,
  "percentStep": 5,
  "strips": [
    { "id": "s1", "color": "green" },
    { "id": "s2", "color": "blue" },
    { "id": "s3", "color": "green" }
  ],
  "orders": [
    {
      "id": "o1",
      "parts": [
        { "id": "o1p1", "color": "green", "percent": 75 },
        { "id": "o1p2", "color": "green", "percent": 25 }
      ]
    }
  ]
}
```

Генерация выполняется до публикации. Runtime RNG отсутствует.

Генератор:
1. Создаёт набор заказов из процентов, кратных `5`.
2. Создаёт фиксированную очередь цветов.
3. Гарантирует, что существует хотя бы один способ закрыть все компоненты заказов.
4. Добавляет лишние полоски и альтернативные проценты так, чтобы preview очереди мог влиять на выбор.
5. Сохраняет готовый уровень в `levels.json`.

Полноценный solver не нужен: генератор сначала строит гарантированно проходную последовательность разрезов, затем перемешивает только заранее допустимые элементы и прогоняет детерминированную проверку.

Кривая по пяти уровням:

1. **Понять проценты.** Один цвет. Один заказ `75% + 25%`. Одна полоска. Игрок учится, что один разрез создаёт два процента и оба могут сразу закрыть заказ.
2. **Понять отходы.** Два цвета. Заказы вроде `зелёный 60%`, `синий 40%`. Игрок видит, что ненужный остаток просто уходит в отходы.
3. **Первый настоящий выбор.** Три цвета и несколько открытых заказов. Для текущего цвета есть два потенциально полезных разреза; preview следующих полосок должен подсказать, какой процент лучше закрыть сейчас.
4. **Давление очереди.** Четыре цвета, 6–8 компонентов. Некоторые цвета встречаются редко; неправильный разрез на редкой полоске делает уровень непроходимым позже.
5. **Проверка концепта.** Минимум 5 цветов и 8–12 компонентов в нескольких корзинах. Пример корзины: `зелёный 25% + синий 60% + красный 40%`. В уровне должно быть минимум три ситуации, где знание следующих 3 цветов меняет лучший текущий разрез.

Если игрок может игнорировать preview и стабильно принимать те же решения, уровень считается невалидным до публикации.

# 7. Визуал

- Рабочая зона: горизонтальный конвейер с одной крупной активной полоской.
- Каждая полоска визуально представляет целое `100%`.
- По длине полоски есть ненавязчивая шкала с шагом `5%`; крупные отметки — `25%`, `50%`, `75%`.
- При тапе появляется линия разреза и два крупных числа, например `60% | 40%`.
- Цвет полоски берётся из `tokens.css`; проценты не кодируются цветом.
- Следующие 3 полоски показываются справа меньшими превью только по цвету и порядку.
- Заказы расположены внизу как корзины с компонентами, например `25% зелёного`, `60% синего`.
- Выполненный компонент коротко схлопывается в чек/заполненный слот.
- Ненужный кусок падает в небольшую зону отходов без дополнительного штрафа.
- Главный payoff: точный разрез, после которого оба куска одновременно улетают в два нужных слота заказа.
- Ошибка как отдельная анимация отсутствует: неправильный процент просто не находит заказ и уходит в отходы.
- HUD: `Заказы: X/Y`, `Осталось полосок: N`, preview следующих 3 цветов.

# 8. Онбординг

1. Каждая полоска — это `100%`.
2. Тапни по ней, чтобы разрезать на две части.
3. Проценты заказа показаны в корзинах внизу.
4. Подходящий цвет и процент автоматически уходят в заказ.
5. Ненужный остаток уходит в отходы.
6. Смотри на следующие цвета и решай, что выгоднее вырезать сейчас.

Кнопка `?` показывает только правило из п.2.

# 9. Явно ВНЕ рамок

- Без меты, валют, коллекций, заданий вне уровня, ежедневных бонусов, рекламы и IAP.
- Без runtime RNG.
- Одно давление: навязанная фиксированная очередь полосок.
- Твист отсутствует.
- Без реального таймера и непрерывного движения конвейера: новая полоска приходит только после валидного разреза предыдущей.
- Без ручного перетаскивания кусков по корзинам — распределение выполняется автоматически по точному совпадению `цвет + процент`.
- Без нескольких разрезов одной полоски, склейки, изменения цвета, бустеров и undo.
- Проценты только с шагом `5%`.
- Без изменений баланса/уровней после публикации, кроме датированного критического бага.

# 10. Метрики и события

Аналитикой владеет общий shell. Механика **не вызывает PostHog напрямую** —
она сообщает о происходящем через контракт `MechanicHost`.

- Shell сам логирует `game_open`, `help_open`, `level_start`, `level_win`,
  `level_5_complete`, `rating_submit`, `comment_submit`.
- Hub отдельно логирует `hub_impression`, `hub_click`, `teaser_click`.
- D1/D7 и повторные сессии PostHog считает сам по persisted distinct_id и
  `game_open` — отдельные события для них не нужны.
- `retry` шлёт shell после fail-попапа; `level_5_complete` отдельно не
  эмитится, он выводится из `level_win` пятого уровня.

Ниже описано, **когда** наступает каждое событие. Механика при этом вызывает
только `onFirstAction()`, `onFail('<код>')` и `onComplete()` — остальное
отправляет shell.

- `first_action` — первый валидный разрез текущей полоски.
- `level_start` — вход на уровень с номером уровня.
- `level_win` — когда выполнены все компоненты заказов.
- `level_fail` — когда очередь полосок пуста, а невыполненные компоненты остались; `reason: 'orders_unfulfilled'`.
- `retry` — повтор того же уровня после fail.
- `level_5_complete` отдельно не эмитится.

Kill-критерий концепта: preview следующих полосок должен реально менять решения. Если прохождение с preview не отличается от прохождения без preview, концепт хоронится, а не чинится дополнительными механиками.

Онлайн-резерв: читаемость, доходимость до 5 уровня, возврат D1. Если критерий не сработал — концепт не чинится.

# 12. Профиль реализации

Относится к фабрике, а не к игровой идее: сменится фабрика — перепишется
только этот раздел.

**Контракт.** Механика реализует `MechanicHost` из `src/shell-contract.ts` и
вызывает `onFirstAction()`, `onComplete()`, `onFail(reason)`, `onExit()`.
PostHog напрямую не трогает — см. раздел 10.

**`game.config.ts`.** `id` совпадает со `slug` из шапки, `title` — с
`title_ru`, `tagline` — короткая строка под названием, `levelCount: 5`,
`version` и `onboarding.version` поднимаются при изменении контента и правил
соответственно. Токены аналитики и ключ обратной связи копируются из
`games/tap-targets/game.config.ts`.

**`data-testid`.** Обязателен на каждом интерактивном элементе — e2e ищет
строго по ним. Существующая конвенция: `game-surface` — контейнер механики,
`mechanic-hud` — HUD с атрибутом `data-remaining`.

**Анимация.** Payoff строится из эффектов `render-kit`: `punch`,
`invalidShake`, `successFlash`, `fadeCollapse`, `cameraShake`, `moveTo`.
Если нужного нет — сказать здесь, а не изобретать свой во время сборки.
_Какие именно эффекты нужны этой игре — не записано._
