# PLAY — правила работы в этом репозитории

Конвейер целиком описан в `docs/PLAY.md`. Это канонический документ: где
что-то расходится с ним, прав он.

---

## Правило №1 — доска не отстаёт от репозитория

**Доска всегда показывает текущее состояние проекта.** Не «после того, как
кто-то вспомнит пересчитать» — всегда.

Делать для этого **ничего не нужно.** Правило держится не на дисциплине, а на
том, что забывать нечего:

1. **Стадии нигде не хранятся.** Нет поля `status`, которое надо переставить
   руками. Стадия — функция от того, какие файлы существуют: есть идея, что
   стоит в `review` спеки, есть ли `game.config.ts`, подписан ли `review.md`,
   заполнен ли `links.play`, снята ли выгрузка, есть ли вердикт. Двигая
   конвейер, ты уже обновил доску — других действий нет.
2. **Снимок собирается на деплое, а не коммитится.** `dashboard/status.json`
   в `.gitignore`. Vercel на каждом пуше выполняет `node pipeline.mjs --write`
   и отдаёт свежий файл. Забыть его обновить невозможно: он не существует в
   репозитории.
3. **Всё, что зависит от даты, страница считает сама, в браузере.** Обратный
   отсчёт до старта, «идёт 12/30 дн.», «месяц вышел», «снять цифры» — это
   меняется без единого коммита, поэтому не запекается в снимок. Правила
   (месяц, тридцать прохождений) приезжают в данных из `pipeline.mjs`, чтобы
   порог оставался записан в одном месте.

Итого: пуш обновляет то, что зависит от файлов; открытая вкладка обновляет
то, что зависит от даты. Ручного шага нет ни там, ни там.

**Почему это вообще правило.** Доска, которая показывает вчерашнее состояние и
выглядит при этом свежей, — худший способ сломаться: ей верят и по ней
принимают решения. **Пустая доска честнее отставшей.**

**Что это значит при изменениях.** Если добавляешь в конвейер новый артефакт
или новую стадию — она должна появиться в `pipeline.mjs`. Не появилась —
доска молча врёт о полноте: показывает всё, кроме нового, и по ней не видно,
что чего-то не хватает. Это единственное место, где правило требует внимания.

Локально доска смотрится так:

```sh
node pipeline.mjs              # в терминале, считает вживую
node pipeline.mjs --waiting    # только то, что ждёт решения
node pipeline.mjs --write && (cd dashboard && python3 -m http.server 8077)
```

## Правило №2 — один источник правды на сущность

Ни одно значение не живёт в двух местах. Если оно нужно где-то ещё — его
читают, а не копируют.

| Сущность | Где живёт |
|---|---|
| Замысел, kill-критерий, оценка | шапка `ideas/active/NN-slug.md` |
| Название, питч, правила игры | `specs/NN-slug.md` (шапка наследует идею) |
| День выхода, ссылки, даты | `games.json` |
| Приёмка спеки | `review` в шапке спеки |
| Приёмка игры | `app/games/<slug>/review.md` |
| Тексты и медиа игры | `app/games/<slug>/media/` |
| Правила и шаблоны постов | `distribution/` |
| Цифры | `data/<slug>.json` |
| Вердикт | `results/NN-slug.md` |

Расхождение шапки спеки с шапкой идеи роняет `specs/validate.mjs`.

## Правило №3 — ворота не пропускаются

Четверо ворот, три из них — решение человека, и ровно они теряются первыми.
Поэтому каждое записано файлом, а не памятью:

| Ворота | Где записано | Кто держит |
|---|---|---|
| Gate 1 — идея | `gate1` + `score` в шапке идеи | `ideas/validate.mjs` |
| Gate 2 — спека | `review` в шапке спеки | `specs/validate.mjs` |
| Gate 3 — CI | зелёный прогон | `.github/workflows/ci.yml` |
| Gate 4 — человек играл | `app/games/<slug>/review.md` | `release.mjs` не публикует без `approved` |

AI ставит баллы и предлагает вердикты. **Решения — человека.** Скрипты не
решают за него: они ловят решение, противоречащее собственным цифрам.

## Проверки перед коммитом

```sh
node specs/validate.mjs       # спеки и сверка с идеями
node ideas/validate.mjs       # Gate 1
node test-hub.mjs             # поведение хаба
node build-games.mjs          # перерисовать страницы из games.json
```

Всё это же гоняет CI. Ошибка роняет сборку, предупреждение — нет.
