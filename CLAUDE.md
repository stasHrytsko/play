# PLAY — правила работы в этом репозитории

Конвейер целиком описан в `docs/PLAY.md`. Это канонический документ: где
что-то расходится с ним, прав он.

---

## Правило №1 — доска не отстаёт от репозитория

**Доска всегда показывает текущее состояние проекта.** Не «после того, как
кто-то вспомнит пересчитать» — всегда.

Делать для этого **ничего не нужно.** Правило держится не на дисциплине, а на
том, что забывать нечего:

1. **Стадии нигде не хранятся.** Нет поля `status`, которое надо переставить
   руками. Стадия — функция от того, какие файлы существуют: есть идея, что
   стоит в `review` спеки, есть ли `game.config.ts`, подписан ли `review.md`,
   заполнен ли `links.play`, снята ли выгрузка, есть ли вердикт. Двигая
   конвейер, ты уже обновил доску — других действий нет.
2. **Снимок коммитится, а забыть его не даёт CI.** `dashboard/status.json`
   лежит в репозитории — тогда страница работает на чистой статике, при любой
   настройке хостинга. Обновляется одной командой, и `node pipeline.mjs
   --check` в CI роняет пуш, если забыл. Проверка гоняется сама и ничего не
   требует включать руками.

   ```sh
   node pipeline.mjs --write
   ```

   *Сборку снимка на деплое пробовали и отказались: команда, читающая файлы
   выше Root Directory, зависит от отдельного переключателя Vercel, а её
   поломка выглядит как пустая страница, а не как красный деплой.*
3. **Всё, что зависит от даты, страница считает сама, в браузере.**
   «Идёт 12/30 дн.», «месяц вышел», «снять цифры» — это меняется без единого
   коммита, поэтому не запекается в снимок. Порог приезжает в данных из
   `pipeline.mjs`, чтобы остаться записанным в одном месте.

   Окно отсчитывается **от даты публикации конкретной игры**, а не от общей
   даты старта проекта: доска показывает, когда игра вышла, и сколько из
   тридцати дней прошло. Общей даты старта на доске нет — она живёт в
   `games.json` и нужна только расписанию постов.

Итого: коммит обновляет то, что зависит от файлов (и CI следит, чтобы
обновил); открытая вкладка обновляет то, что зависит от даты.

**Почему это вообще правило.** Доска, которая показывает вчерашнее состояние и
выглядит при этом свежей, — худший способ сломаться: ей верят и по ней
принимают решения. **Пустая доска честнее отставшей.**

**Что это значит при изменениях.** Если добавляешь в конвейер новый артефакт
или новую стадию — она должна появиться в `pipeline.mjs`. Не появилась —
доска молча врёт о полноте: показывает всё, кроме нового, и по ней не видно,
что чего-то не хватает. Это единственное место, где правило требует внимания.

Локально доска смотрится так:

```sh
node pipeline.mjs              # в терминале, считает вживую
node pipeline.mjs --waiting    # только то, что ждёт решения
node pipeline.mjs --write && (cd dashboard && python3 -m http.server 8077)
```

## Правило №2 — один источник правды на сущность

Ни одно значение не живёт в двух местах. Если оно нужно где-то ещё — его
читают, а не копируют.

| Сущность | Где живёт |
|---|---|
| Замысел, kill-критерий, оценка | шапка `ideas/active/NN-slug.md` |
| Название, питч, правила игры | `specs/NN-slug.md` (шапка наследует идею) |
| День выхода, ссылки, даты | `games.json` |
| Приёмка спеки | `review` в шапке спеки |
| Приёмка игры | `app/games/<slug>/review.md` |
| Тексты и медиа игры | `app/games/<slug>/media/` |
| Правила и шаблоны постов | `distribution/` |
| Цифры | `data/<slug>.json` |
| Вердикт | `results/NN-slug.md` |

Расхождение шапки спеки с шапкой идеи роняет `specs/validate.mjs`.

### Дерево

```
trends/YYYY-MM-DD-тема.md      наблюдения по рынку           ← пишет человек
ideas/active/NN-slug.md        идея + оценка + Gate 1        ← человек, оценка AI
ideas/rejected/NN-slug.md      не прошла Gate 1
specs/NN-slug.md               спека + Gate 2                ← AI, принимает человек
app/                           фабрика: общий шелл и игры
app/games/<slug>/              код одной игры                ← AI по спеке
app/games/<slug>/review.md     Gate 4: человек играл         ← человек
app/games/<slug>/media/        обложка, баннер, кадр, ролик, тексты
data/<slug>.json               воронка из PostHog            ← скрипт
results/NN-slug.md             метрики + вердикт             ← AI, утверждает человек

games.json                     реестр: день → слаг, статус, ссылки, даты
g/<slug>/                      опубликованная сборка         ← release.mjs
distribution/                  каналы, шаблоны, прогрев, генератор CSV
dashboard/                     доска страницей
docs/PLAY.md                   конвейер целиком — канонический документ
docs/decisions.md              журнал решений проекта
docs/templates/                шаблоны идеи, ручной проверки, медиа

specs/front-matter.mjs         чтение YAML-шапок — общее для всех скриптов
specs/validate.mjs             Gate 2 и сверка шапок с идеями
ideas/validate.mjs             Gate 1
pipeline.mjs                   доска: стадии и что ждёт человека
release.mjs                    публикация одной игры на хаб
build-games.mjs                генератор хаба
test-hub.mjs                   проверка поведения хаба
.github/workflows/ci.yml       Gate 3
```

`NN` — номер концепта, а не день выхода. Концепт 23 может выйти в день 5;
связь «день → слаг» живёт только в `games.json`.

## Правило №3 — ворота не пропускаются

Четверо ворот, три из них — решение человека, и ровно они теряются первыми.
Поэтому каждое записано файлом, а не памятью:

| Ворота | Где записано | Кто держит |
|---|---|---|
| Gate 1 — идея | `gate1` + `score` в шапке идеи | `ideas/validate.mjs` |
| Gate 2 — спека | `review` в шапке спеки | `specs/validate.mjs` |
| Gate 3 — CI | зелёный прогон | `.github/workflows/ci.yml` |
| Gate 4 — человек играл | `app/games/<slug>/review.md` | `release.mjs` не публикует без `approved` |

AI ставит баллы и предлагает вердикты. **Решения — человека.** Скрипты не
решают за него: они ловят решение, противоречащее собственным цифрам.

Каждое ожидающее решение доска показывает с адресом: какой файл открыть, что
в нём прочитать и куда записать ответ. Это не удобство, а условие того, чтобы
ворота проходились: пункт без адреса откладывается, потому что начинается с
вопроса «а где это».

**Добавляя новую стадию или новые ворота, пропиши в `pipeline.mjs` и действие**
— `open`, `read`, `write`, при необходимости `run`. Строка «ждёт решения» без
них выглядит рабочей и при этом бесполезна.

**И пропиши, что делать, когда поля просто нет.** Ветка «значения нет» — это
не «нечего делать», а чаще всего «никто ещё не занимался». Спеки 1–35 писались
до появления Gate 2, и `pipeline.mjs` на отсутствующий `review` не делал
ничего: ни ожидания, ни пометки. Тридцать спек, не прошедших ворота, выглядели
на доске так же, как пройденные. По пустой клетке нельзя отличить «сделано» от
«не дошли руки» — поэтому пустых клеток быть не должно. (Сейчас у всех тридцати
стоит `review: pending`, то есть они честно в очереди на Gate 2.)

**Очередь, а не свалка.** Gate 2 нужен всем тридцати спекам, но игры делаются
по одной, поэтому в «ждёт тебя» попадает только ближайшая по расписанию;
остальные помечены в таблице и ждут очереди. Тридцать одинаковых пунктов
утопили бы всё остальное — а список, в который не смотрят, не лучше пустого.

## Проверки перед коммитом

```sh
node pipeline.mjs --write            # снимок доски
node build-games.mjs                 # страницы хаба из games.json
node distribution/build-posts.mjs    # CSV расписания постов и превью текстов
node specs/validate.mjs              # спеки и сверка с идеями
node ideas/validate.mjs              # Gate 1
node test-hub.mjs                    # поведение хаба
```

Первые три — генераторы, их выход закоммичен. CI проверяет, что закоммиченное
совпадает с тем, что генераторы дают из текущих источников: забыть перезапустить
нельзя, пуш покраснеет. Остальные три — проверки; ошибка роняет сборку,
предупреждение нет.

**Сгенерированное руками не правят.** `index.html` и страницы игр,
`dashboard/status.json`, `distribution/publer-posts.csv`,
`distribution/posts-draft.md` — выход генераторов. Править надо источник:
`games.json`, шапку спеки, `posts.json`, `media/copy.md` игры.
